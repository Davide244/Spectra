# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Spectra Engine is a high-performance, cross-platform game engine in C#/.NET 10.0, targeting an editor inspired by HAMMER and Roblox Studio. It pairs a scene graph with runtime CSG/BSP world geometry, renders through Silk.NET (OpenGL, D3D11, and D3D12 working; Vulkan planned, blocked on SPIR-V codegen), and ships its own shader language (SpectraShade) that cross-compiles to GLSL and HLSL.

## Build & Test Commands

```bash
dotnet build                                        # Build the solution (Spectra.slnx)
dotnet run --project SpectraEngine.Executable       # Run the demo (args: opengl | d3d11 | d3d12, and --selftest)
dotnet run --project SpectraEngine.Executable -- d3d11 --selftest   # ...with the editing self-test on (default OFF)
dotnet run --project SpectraEngine.Executable -- d3d12 --fullscreen-cycle=2   # ...toggling fullscreen every 2 s (default OFF)
dotnet run --project SpectraEngine.Executable -- d3d11 --play          # ...starting in first-person play mode (default OFF; F8 toggles it)
dotnet run --project SpectraEngine.Executable -- d3d11 --save-map=Out.smap   # ...writing the scene out as a .smap bundle (a FOLDER of text)
dotnet run --project SpectraEngine.Executable -- d3d11 --map=Out.smap        # ...running that bundle instead of the authored demo scene
dotnet run --project SpectraEngine.Executable -- d3d11 --save-project=MyGame  # ...exporting the scene as a standalone project folder
dotnet run --project SpectraEngine.Executable -- d3d11 --save-project=MyGame --exit-after-save  # ...and shutting down after one frame, for an unattended caller
dotnet run --project SpectraEngine.Executable -- d3d11 --project=MyGame       # ...running a project: its Assets are the content root, its startupMap boots
dotnet run --project SpectraEngine.Executable -- d3d11 --export-entity-schema=Game.sentdef  # ...writing this build's entity schemas out and EXITING (no window, no session)
dotnet run --project SpectraEngine.Executable -- d3d11 --viewport-compare  # ...the double-sRGB-encode gate: one frame into the shared target AND an ordinary sRGB one, compared byte for byte, then EXIT (d3d11 | d3d12; no window)
dotnet run --project Test/SpectraShade.Compiler.Tests    # Compiler tests (xUnit v3 on MTP)
dotnet run --project Test/SpectraEngine.Bsp.Tests        # CSG/BSP + scene (events, BVH, id index) tests
dotnet run --project Test/SpectraEngine.Editing.Tests     # Editor input frame, commands, undo/transactions, gizmos
dotnet run --project Test/SpectraEngine.Graphics.Tests   # GL smoke tests (real driver/context)
dotnet run --project Test/SpectraEngine.Editor.Tests     # Shell scene-tree replay, virtual-key table, viewport input router
dotnet run --project Test/Spectra.Kitchen.Tests           # Pack container: format layout, writer, reader, cook, cooked-only validation
dotnet run --project Spectra.Kitchen.CLI -- cook <projectDir>    # scook: cook a project into a .spack
dotnet run --project Spectra.Kitchen.CLI -- verify <pack>        # ...prove it decodes and resolves with only itself mounted
dotnet run --project Spectra.Kitchen.CLI -- inspect <pack> [--json]  # ...list its header and entries
dotnet run --project Test/SpectraEngine.Physics.Tests     # Character mover, collision source, Box3D sync
dotnet run --project Test/SpectraEngine.Entities.Tests    # Entity generator, built-in classes, .sentdef writer/reader
dotnet run --project SpectraEngine.Editor -- d3d11       # Avalonia editor shell (d3d11 | d3d12; Windows only)
dotnet run --project SpectraShade.Compiler.CLI -- <file> # ssc shader compiler
dotnet run -c Release --project Benchmarks/CsgBench      # CSG/BSP benchmark (optional filters: grid | floorplan | tower | query | incremental | openworld)
dotnet publish SpectraEngine.Executable -c Release -r win-x64   # NativeAOT demo build (do NOT add -p:PublishAot=true, see below)
git submodule update --init --recursive              # fetch the pinned Box3D source
native/build-box3d.ps1                               # build box3d.dll (win-x64 Release; -Rid/-Config/-Clean)
```

Test projects run via `dotnet run` (xUnit v3 on Microsoft.Testing.Platform), not `dotnet test`.

`--fullscreen-cycle[=seconds]` is the second piece of gate instrumentation, and OFF by default for the same reason as the self-test: it starts a driver thread that hits the window-mode latch on a timer, so an unattended run performs the windowed ↔ borderless-fullscreen transition a human does with F11 while the render thread keeps presenting and resizing the swap chain. That is the crash this repo fixed — a run must log a `Window mode -> …` line per toggle, survive all of them, and keep the recompile counter and chunk-culling counts moving afterwards, with nothing at `ERR`. Nobody wants a window that reshapes itself every two seconds interactively, so it has to be asked for.

**F8 walks the demo.** The engine installs a `FirstPersonController` over the scene and `--play` (or F8) enters play mode: the cursor locks, the camera drops to eye height, WASD/Shift/Space drive a real `CharacterMover` inside the fixed tick loop, and Escape or F8 leaves and puts the camera back exactly where it was. F9 draws the capsule and its ground normal — useful only from outside your own head, which is what leaving play mode is for. The character spawns in `DemoPlayArea`, a human-scale obstacle course authored at x = 150, deliberately **beside** the original demo room rather than replacing it: that room is 6x6 sunits with a 1.2-sunit doorway, which a 1.8-sunit character cannot use, and the door must stay exactly that size because its coincident planes are the flush-coplanar-cut regression fixture. The course brackets the tuning rather than sampling it — stairs at 0.25 / 0.40 / 0.50 rises against a 0.45 step height, ramps at 25 / 40 / 55 degrees against a 46-degree slope limit, a 2.2 x 1.4 doorway and a tunnel both cut by subtractive brushes, a 3-unit chasm cut clean through the slab, and a part brush to stand on — so `DemoPlayAreaTests` walks the actual level and fails when a *constant* moves, which no mover unit test can see.

A ~15-second demo run is a smoke gate in its own right — **run it with `--selftest`** (or `SPECTRA_SELFTEST=1`), which is off by default: it must then log `Editing self-test: PASS` about every five seconds (see the self-test bullet below) and nothing at `ERR`. Without the switch the demo is quiet and nothing synthetic touches the scene, which is what an interactive run must be.

**Native code needs no Developer Command Prompt, and using one is not the fix for anything here.** Box3D is a git submodule at `external/box3d`, pinned to an exact commit, built by `native/build-box3d.ps1` — and CMake's Visual Studio generator locates MSVC through the registry and drives MSBuild itself, so `cl` on `PATH` is irrelevant to that build. Verified: CMake 4.2.3 → Visual Studio 18 2026 → MSVC 14.50.35717 from an ordinary shell. **The NativeAOT publish below is the genuinely different case** — it shells out to the ilcompiler's `findvcvarsall.bat`, which *does* care. Do not generalise one to the other. The build options are a contract and live in that one script (notably `BOX3D_DOUBLE_PRECISION=OFF`, which is ABI-affecting rather than a tuning knob); output lands in `native/runtimes/<rid>/native/` and is deliberately NOT committed, because the submodule SHA is what is under version control and a binary that can drift from it is worse than none. See `native/README.md`.

**Never pass `-p:PublishAot=true` on the publish command line.** `PublishAot` is already set in the three projects that want it (`SpectraEngine.Executable`, `SpectraShade.Compiler.CLI`, `Spectra.Kitchen.CLI`), so the switch is redundant, and it is worse than redundant: a command-line `-p:` is a GLOBAL property that reaches **every project in the graph**, including `SpectraEngine.Entities.Generator`, which targets `netstandard2.0` because a Roslyn analyzer must. The SDK then refuses the whole publish with `NETSDK1207` naming the generator, which is not where anything is wrong. A global property cannot be overridden from inside the project it lands on, and `UndefineProperties` on the analyzer's `ProjectReference` does not help either, because the failure happens during **restore**. Dropping the switch is the fix; the reference carries `UndefineProperties` as well, for the build graph.

The NativeAOT publish shells out to the MSVC linker through the ilcompiler's `findvcvarsall.bat`, and VS 2026's `vcvarsall.bat` calls `vswhere.exe` unqualified. If `C:\Program Files (x86)\Microsoft Visual Studio\Installer` is not on `PATH`, the batch file's error text is captured as the linker path and the publish dies with `MSB3073 ... exited with code 123` — nothing to do with the code. Publish from a Developer prompt, or prepend that directory to `PATH`.

## Project Structure

- **`Assets/`** — The repo's content root: real files, loaded from disk, never embedded in code. `Textures/` (PNG dev textures), `Materials/` (`.spectramat` text), `Models/` (`.obj` + `.mtl`, `.gltf` prop fixtures), `Logo/`. Copied to `<output>/Assets` by `SpectraEngine.Core.csproj` so a deployed build resolves the same relative paths.
- **`SpectraEngine.Core/`** — Engine library: `Engine` (window + dedicated render thread), `Graphics/` (Renderer abstraction; OpenGL, D3D11, and D3D12 backends; forward/wireframe pipelines; shader hot-reload; DebugDraw; debug-layer message drains on both D3D backends), `Scene/` (SceneNode graph, Camera, SceneManager, `ModelInstantiator`), `Bsp/` (Brush, per-face `FaceSurface`, CSG carve/snap/weld, solid-leaf BSP), `Input/`, `Assets/` (`ContentRoot` resolution; typed caches for textures, materials and models; `ImageDecoder`/`ModelImporter` background decode + render-thread upload pump; `.spectramat` parsing; `MaterialRef`/`MaterialRegistry` interning), `Audio/` (OpenAL device/context/listener, a 32-source pool, `StreamingVoice`, and the sample-frame loop arithmetic that replaces `AL_LOOPING`), `Diagnostics/`.
- **`SpectraEngine.Editing/`** — Editor-only layer, deliberately a separate assembly so gizmo/undo/tool code never ships inside an AOT game binary: `Input/` (`EditorInputFrame`, the immutable per-frame input snapshot every tool consumes, plus the `IEditorInputSource` adapter seam), `Commands/` (`IEditorCommand` addressed by `SceneNode.Id`, absolute before/after transform commands, `SetBrushCommand` for brush swaps, `CompositeCommand`), `Undo/` (`UndoStack`: bounded ring history, redo invalidation, gesture transactions), `Gizmos/` (`GizmoTool` base + `TranslateGizmo`/`RotateGizmo`/`ScaleGizmo`, shared `GizmoGeometry`/`GizmoHitTesting`/`GizmoColors`/`SnapSettings`, and `GizmoController` with its `GizmoCommand` verbs), `Selection/` (`BoxSelectController` marquee, `ScreenRect`, `SelectionModifiers`), `Cameras/` (`EditorCameraController`: Roblox-Studio navigation — right-drag freelook with a real cursor lock, WASD/QE fly, Alt-drag orbit, middle-drag pan, zoom-toward-the-cursor, frame-the-selection), `Viewport/` (`ViewportInteractionController` — the one press, three meanings arbitration that decides between manipulate, select-and-move and box select). References Core and **nothing else — no Silk.NET, no `IWindow`** (a test asserts it).
- **`SpectraEngine.Editor/`** — The Avalonia editor shell, and the engine's second host: `Viewport/` (`EngineViewport`, a `NativeControlHost` that creates a real Win32 child window; `Win32/` holds the window class, its message loop and the virtual-key table), `EditorSession` (renderer, managers and editor wired exactly as the demo wires them, then `Engine.Start` instead of `Engine.Run`), `SceneTreeModel` (the graph mirror built from `FrameSnapshot`s), `MainWindow`. Windows-only for now: an embedded OpenGL viewport needs its own WGL context, which is not built.
- **`SpectraEngine.Executable/`** — Thin bootstrapper; picks backend from argv, wires managers, runs the demo scene. Also the engine's editor host: `Editing/` holds `DemoEditorHost` (the `ISceneEditor` implementation — input frame, keymap, viewport, editor camera, undo history) and `EditingSelfTest` (the headless PASS/FAIL proof of the whole manipulation chain). It and `SpectraEngine.Editor` are the only projects that reference `SpectraEngine.Editing`, which is what keeps gizmo/undo/tool code out of a shipped game binary.
- **`Spectra.Kitchen/`** - The cook: pack **writers** and cook rules, and they live here and nowhere else, so no shipped game binary carries pack-writing code. Bound by AOT-safe dependencies regardless of its CLI, because the editor must host it in process for cooked-accurate preview and a cook that only runs out of process cannot do that. `Spectra.Kitchen.CLI` produces `scook`. Pack **readers** live in Core (`Assets/Packs/`), because a shipped game reads packs and writes none.
- **`SpectraShade.Compiler/`** — Shader language: lexer → parser → analyzer → codegen (`GlslGenerator`, `HlslGenerator`, `SpirVGenerator` stub, shared `TypeInference`). See `LANGUAGE.md` / `FEATURES.md`.
- **`SpectraShade.Compiler.CLI/`** — `ssc`, AOT-published. Default targets: opengl, d3d11, d3d12 (vulkan is opt-in until SPIR-V exists).
- **`SpectraShade.LSP/`** — Language server (diagnostics + completions) over stdio.
- **`SpectraShade.VSIX/`** — Visual Studio extension (net472): TextMate grammar, item templates, bundled LSP.

## Architecture Decisions

- **Content reaches the engine through ONE seam, and strictness belongs to the SOURCE STACK rather than to `AssetManager`.** `IContentSource` (`Assets/Sources/`) is read-only, thread-safe and GPU-ignorant; `LooseFileSource` is the filesystem, a pack is another source, and `ContentSourceStack` flattens them by priority band at MOUNT time rather than probing per lookup. **The delicate part is arithmetic, not design: `AssetManager` reached the filesystem in seven places, not the one that is obvious** (the texture decode, a separate existence probe when binding a texture slot, the material parse, the existence half of the material load, the async decode twin, the model-material override probe, and watcher registration). If those do not move together the existence check disagrees with the open, and the symptom is that materials in a packed build silently never resolve their textures while every log line reads healthy. `TryOpen` never throws. `ContentBlob` is disposable and pooled today **because it will hold a span into a memory-mapped view tomorrow**, and that ownership contract has to exist before the thing it protects does. Strict mode throws on a total miss, and it is a property of the stack precisely because `AssetManager`'s degradation to a default material and a magenta texture is a pinned invariant that must not become conditional on where content came from. Hot-reload watchers attach through `TryGetWatchPath`, so a source with no watch path is simply not watched, and pure-pack mode reports hot reload off **with a reason** rather than silently no-opping. Model FILES still read from disk (the importer takes a path); model materials and textures already resolve through the stack.
- **A `.spack` is one memory-mapped file, and `PackHandle`'s refcount is not a follow-up.** The container earns being custom on two axes a zip cannot serve: an id-keyed table that binary-searches **in place** over the mapped view, and payloads aligned so they reach the GPU without a copy. Entries sort by an unsigned 128-bit XxHash128 of the **normalized content-relative source path** - the same string `ContentRoot.NormalizeRelativePath` already produces, because asset identity must be one thing whether content came from a folder or an archive, which is what makes the whole asset layer a source swap rather than a rewrite. **Unmapping a view while a span into it is alive is an access violation, not an exception**: no managed stack, no catch block, and the asset manager's upload queue carries spans to the render thread, so every `ContentBlob` holds a reference and the reference travels with it. Map the WHOLE file once - Windows view offsets must be multiples of the 64 KB allocation granularity rather than the 4 KB page size, and a per-entry view is how that gets discovered the hard way. Every reserved byte is zero-filled deliberately, because an unzeroed field picks up stack garbage and turns a byte-identity oracle red in a way that is very hard to bisect. The trailing digest is **corruption detection and a patch-diff key, never tamper resistance**, and the doc says so because a hash at the end of a file invites that misreading. `EntryTableOffset` is written explicitly although it is always 64 today, so the header can grow without spending a version number. Priority bands and the tombstone kind ship in v1 with nothing mounting a second pack: they are the mod and patch story, they cost nothing now, and adding them later would be a format change rather than a feature.
- **A pack that mounts cleanly can still be broken, and `scook verify` is the only thing that can see it.** Mounting proves the container and says nothing about whether a material's texture was cooked; the runtime's answer to a missing texture is a magenta placeholder and a warning, so a cook can succeed, a pack can mount, every log line can read healthy, and the shipped game shows checkerboards. **`PackVerifier` resolves every in-pack reference through a `ContentSourceStack` carrying the pack and NOTHING ELSE, strict**, and both halves are the feature: alone, because the editor mounts loose files ABOVE the pack and would otherwise answer out of the source tree and prove nothing; strict, because a miss must THROW here where the identical miss degrades in a frame. Those are one lookup with two consequences, which is exactly why the consequence belongs to the stack rather than to `AssetManager`, whose degradation is a pinned invariant. **The four claims are independent and one is only reachable because the fixtures re-stamp the digest**: any edit breaks the trailing hash, so without a re-stamp every corruption test is the same test and nothing past the mount ever runs - re-stamping separates a bit that rotted on disk (`SC9003`) from bytes that were never valid (`SC9004`, a payload rewritten together with the hash over it, which verifies correctly and is still not a deflate stream). The table check is a claim about the FILE, not about the writer: `PackWriter` sorting is a statement about the code that wrote a pack and `SC9005` is a statement about the bytes, which is the only one of the two that survives the file being edited afterwards. **A diagnostic reports in the band of the failing SUBSYSTEM** (a texture nobody cooked is `SC5001`, not a pack code), which is what makes `CheckReferences` growable one arm per format: `.smodel` to 3xxx, `.scmap` to 7xxx, a shader blob per backend to 6xxx. The editor's **Validate Cooked** cooks first every time, because a stale pack passing answers a different question than the one being asked, and it runs off the UI thread naming no `Scene`, so it needs no `EnqueueCommand`. **The CI gate is a job of its own** (`cooked-windows`) because every other suite resolves loose files: the export half needs a real device and is best-effort with a timeout, gated on the ARTIFACT rather than the exit code (the demo host installs Box3D unconditionally, no job builds `box3d.dll`, so it can export and then die), while `Test/Spectra.Kitchen.Tests` cooks the engine's own `Assets/` and verifies them on both hosts either way. **`--exit-after-save` cannot be an exit-before-a-window like `--export-entity-schema`** - a schema is a fact about the build and a saved scene is the scene, which does not exist until meshes and textures do - so it is a real run exactly one frame long, ended through `EngineHost.RequestShutdown` because the handler is raised on the render thread, and refused outright without a save path to pair with.
- **Shaders are COOKED now, and the whole point is that a shipped game compiles none.** `ShaderRule` runs the SpectraShade compiler IN PROCESS - which is the reason `Spectra.Kitchen` is bound by AOT-safe dependencies at all, since the editor hosts it for cooked-accurate preview and a cook that can only shell out to `ssc` cannot be hosted - and emits one `.specshadecomp` per source under `PackEntryKind.Shader`. **The target filter is applied on the WRITER side as well as by asking the compiler for fewer backends**: a pack cooked for d3d11 must not carry a GL blob, and trusting the compiler to return exactly what it was asked for makes the promise a property of another component. The rule declares `CookSettingKeys.Targets` and nothing else, so a `--profile fast` run does not recompile a project's shaders while a changed `-t` list does; `IRuleContext.Targets` is how it reaches a rule, because handing a rule the whole `CookSettings` would let it read a setting it never declared and the cache key is built from the declaration. **A compiler diagnostic reports under `SC6001` rather than a wrapped `SS####`, and that is a placeholder for a wrap rather than a decision against one**: SpectraShade's `Diagnostic` carries a severity, a message and a span and NO number anywhere in the compiler, so minting one here would put a code on the compiler's behalf that `ssc` and the language server do not agree with, which is the exact failure `CookDiagnosticId.Wrap` exists to avoid.
  - **The engine resolves a built-in shader through the content stack: cooked blob, then source, then the copy embedded in the assembly, and the ORDER is the feature.** `BaseShaderResolver` is that lookup and `Renderer.ShaderContent` is where the stack arrives (set by `Engine` BEFORE `Initialize`, or a pack would be ignored for exactly the two shaders every frame binds). A built-in is an ASSET PATH first - `Shaders/Lit.spectrashade` and `Shaders/Lit.specshadecomp`, derived the same way on both sides so the pack's entry and the engine's lookup cannot be spelled differently. **There is no existence probe before the open**, because the documented failure in this content layer is an `Exists` that disagrees with the `TryOpen` beside it. Every degradation is silent and therefore stated: a cooked file with no blob for this backend is reported at Error and falls through to source (refusing would turn a mis-targeted pack into a black window, and the source path renders the right frame); a packed source has no watch path and is simply not watched; and the developer tree's own FILE is still read where there is one, because the embedded resource is a snapshot taken at build time and serving it would make an edit invisible until a rebuild while the watcher beside it went on claiming hot-reload was live. **The eight sites that used to spell out "source path if there is one, else the embedded copy" are now one call each**, which is what makes the cooked path reachable at all.
  - **`ReadPipeline` has a SPAN twin over the same `ShaderFileLayout`.** A mounted pack hands out a span into a memory-mapped view, and wrapping one in a `MemoryStream` copies the whole file to reach one blob - the copy the container exists to avoid. Two parsers, one layout, and `ShaderFileCodecTests` asserts they agree byte for byte on a multi-pipeline file, because a divergence between them is a stage read out of the middle of somebody else's bytes rather than an exception. The span parser refuses a truncated file where `BinaryReader.ReadBytes` would hand back a short array. **`PackVerifier` grew the 6xxx arm** the class already had a place reserved for: every cooked shader must carry a blob for every backend the pack was cooked for, reported as `SC6002` naming the shader and the backend. A pack does not record what it was cooked FOR, so with no `--target` the expectation is the UNION over the pack's own shaders - deliberately weaker, catching the failure that actually happens (one shader short of what every other shader in the same pack managed) and not a pack whose shaders are uniformly a backend short, which is why `scook verify --target` is authoritative when given. **The engine's own built-ins are NOT in any pack yet**: they are embedded resources outside `Assets/`, the walker only walks the content root, and injecting them would mean a rule reading something other than the filesystem. The resolution path is live and takes them the moment a pack carries them.
- **The cook runs on N workers and the ORDER is not one of the things that varies.** `CookSession` builds the whole work list on the calling thread in walk order, runs one level of it in parallel, and writes results into a pre-sized array indexed by WORK ITEM, never appended in completion order; everything that decides a byte (diagnostics, `PackWriter.Add`, the loose tree, the counters, the manifest rows) is then applied on the calling thread in that index order. `-j1` goes through the same call rather than a serial twin, because a second implementation is a second thing to keep in step. There is still exactly ONE level, and that is honest rather than provisional: no rule depends on another rule's output yet, so a level is expressed as a RANGE of the work list and a real DAG later sorts the list instead of changing an ordering rule. **The three oracles run the real `scook` through `Process.Start`, and that is the whole point of them**: .NET's string hash seed is per PROCESS, so an in-process comparison structurally cannot detect the hash-order dependency they exist to catch. Two clean cooks in two processes match, a cached cook matches a clean one, `-j1` matches `-j8`; oracles 1 and 3 compare the MANIFEST as well as the pack, because the pack sorts by asset id and would absorb a scheduling leak exactly where one first appears. They were checked against a deliberately broken build and went red, which is the only evidence that an oracle bites. `ContentStore` deliberately takes no lock: its temp-file-plus-atomic-rename already survives concurrent writers AND other processes, which no in-process lock could.
- **A cooked model is ONE vertex buffer with submeshes as index ranges, and it is read as a `ref struct` over the mapped bytes.** `.smodel`'s submeshes and LODs are ranges rather than separate buffers because an LOD switch has to be a draw-range change rather than GPU resource churn, which is the opposite of a `.scmap` chunk, whose submeshes really are uploaded and destroyed per cell: both mirror their runtime artifact rather than one shape being imposed on both. `SmodelModel` is a `ref struct` so a model provably cannot outlive the mapping its spans point into. **An unknown section FourCC is SKIPPED**, which is what lets `SKEL`, `COLL` and `ANIM` be designed now and written later with no version bump. `COLL` is plane-set hulls because that is exactly `Brush`'s constructor input, so cooked collision rides the existing character machinery with no new collision code, and its plane array is realigned to 16 inside the section because `4 + hullCount * 8` is not 16-aligned for any odd hull count and the in-place cast is the entire reason the section is shaped that way. Index VALUES are deliberately not validated (that is O(indices) and would spend on load what the zero-copy layout saves); submesh RANGES are checked against `IBUF`, which is the bound that turns a malformed file into a wrong picture rather than a read past the end. That trade assumes a pack this cook produced, and is the first thing to revisit if untrusted packs ever mount.
- **An entity is STRINGS on the node, and the runtime never writes back.** `SceneNode.Entity` is a mutable `EntityData` payload (classname, an ORDERED keyvalue list, connections) which is exactly the document model; runtime `Entity` instances are built from it and exist only while an `EntityWorld` is active. That single decision buys three things: the editor shows schema-driven properties with no runtime at all, play/stop needs no state capture because nothing authored was disturbed, and an unknown class is lossless for free because the store was always strings. **Keyvalues are a LIST, not a dictionary**, because member order must round-trip byte-identically through the map and dictionary iteration order is the same determinism sin the carve and the cook already refuse. **Times-to-fire decrements on the runtime copy of the wires, never on the stored ones** - decrementing authored data is corruption that survives to the next save and stays invisible until somebody diffs a map. Activation is two-phase (construct and parse all, then index and copy wires, then spawn all, then activate all); collapse it and an entity's spawn fires at a target that does not exist yet, intermittently, depending on graph order. ONE min-heap keyed on (fireTime, monotonicSequence) carries think wakeups and pending outputs together, because two heaps make ordering total within each and undefined between them, and the per-tick dispatch budget trips at Error **naming the targetname and output**, since the failure it catches is a zero-delay mutual relay that otherwise hangs the render thread with no clue. `EntityCatalog` enumerates in **classname order, never registration order**: module-initializer order is loader-dependent and the binary schema this feeds must be byte-stable across runs. The payload is COPIED on `Clone` for the same reason `Light` is - it is mutable. `targetname` IS `SceneNode.Name`, one identity, and a keyvalue trying to shadow it is a generator diagnostic.
- **`.sentdef` is how a schema leaves the process, and `EntitySchemaCatalog` can be built from NOTHING ELSE.** That refusal is the whole design rather than a style rule: the editor's property panel and its wiring UI are consumers of `EntitySchema` and of no other input, so a second population path taking a schema list would let an in-process editor read `EntityCatalog` directly while an out-of-process one read the file, and the two producers a Luau definition and a generated C# class are meant to be indistinguishable through would drift with nothing failing. Going through the bytes also means `SceneManager` exercises the round trip on **every scene load**, so a layout mistake surfaces where somebody is looking rather than the first time a game exports its definitions. **Writer, reader and layout constants live in one file** (`SentDef.cs`), because two halves of a byte layout in two files drift into a file that parses into different numbers than it was written from, and nothing throws. **`RecordSize` includes itself and the walk advances by it and by nothing else** - that one line is the forward compatibility, and it only works if a reader never derives the next record's position from what it managed to parse; content a record has no room for is refused, trailing bytes it did not ask for are skipped, and `SentDefTests` proves the second record survives the first one growing. **NaN means unbounded and is asked with `float.IsNaN`**, never `==`, which reports every bound as present and then clamps against a NaN. **Reserved flag bits are REFUSED at the write and masked on the read**, deliberately asymmetric: a writer that quietly dropped bit 3 would let the first real producer of replication ship a file missing it while every parity test still passed, whereas a file some other tool wrote must lose what this build cannot honour. The `Origin` byte is an editor badge and the parity pin is already written against it - one class, two origins, byte-identical apart from that byte - held in trust for the day Luau-defined entities need an oracle. Two things the spec left open are settled in the file and folded back into `docs/formats-and-pipeline.md`: the choice record's shape, and that its `HeaderSize = 16` is four short of its own field table.
- **The shell renders entity rows, and entities are insertable, off ONE session-owned catalogue.** `EditorSession` serializes `EntityCatalog.Shared` to `.sentdef` bytes at construction and parses them straight back, assigning the result to `SceneManager.EntitySchemas` so the render thread stamps every scene with the SAME instance the UI thread reads. That is not ceremony: the Insert menu is a list of what a session can place and the panel's badge is a claim about what a class declares, and built from `EntityCatalog.Shared` instead they would answer a different question from the panel the day a project ships a `.sentdef` this process has no C# for. One instance is what makes them provably the same answer, and it exercises the round trip on every launch rather than only in a test.
  - **A row's identity is the PAIR `(PropertyId, Key)` all the way through the shell, and the shape comparison is where that bites.** Every keyvalue an entity declares wears one id, so two classes declaring the same NUMBER of properties compare equal on ids alone, the panel keeps the controls it already built, and the refresh pours one key's value into another key's box - no throw, no log, and a commit writes it there. `PropertyRowShape` already compares both halves; what the shell had to grow is the `Key` on `PropertyRowModel` and on every `PropertyEdit` it emits, since an edit carrying the id alone names no property at all and `PropertyEditor` refuses it rather than guessing.
  - **An entity row's value crosses as WIRE TEXT whatever widget the schema asked for**, converted in one place through `KeyvalueWire`. A keyvalue's storage IS its wire string, so a number cell over an `Int` and a checkbox over a `Bool` both commit text; `PropertyEditor`'s entity arm reads `Text` and nothing else, and an edit arriving with only `Number` set would write the empty string over whatever the author had. A per-axis vector edit sends all THREE components, because the merge splices at the TOKEN level and writes the value whole when either side is not exactly three parts - which for a one-token string replaces a whole vector with a single number.
  - **An unknown class gets a standing AMBER badge, not silence and not an error.** The rows below it are still that map's own data, editable and preserved byte for byte - that is what makes a map from a game this build does not have worth opening - so what is missing is only the schema, and without saying so a mistyped class name looks exactly like a class with nothing declared. Amber because it is STATE (`SpectraMode`), never the accent, which means selection, and never the danger colour. A MIXED classname gets no badge: naming one class as missing would be a lie about the other four.
  - **A fresh entity starts with EMPTY keyvalues, and the tree's glyph is a diamond.** Omit-at-default is the rule the map format already keeps: the panel shows the schema's declared defaults and a commit producing the value the entity already effectively has records nothing, so a key appears in the file exactly when somebody changed it - seeding the whole schema into every map would make a later change to a default reach no level ever saved. The node's name is the CLASSNAME, because the name IS the targetname and there is no second identity to invent one from; duplicates are legal and mean something, and every other insert produces a duplicate name too. The glyph is a plain diamond, the only non-cube non-sphere silhouette in the set, because an entity has no shape of its own to draw; its tint is the last unspent hue in the kind palette, and it earns a saturated one for the reason a cut does - an entity renders nothing at all, so the tree is the only place one can be found. `t:entity` resolves through the hand-written alias table, including the `entitie` stem the plural rule's `TrimEnd('s')` actually produces.
  - **Both entity submenus are BUILT IN CODE, from one function.** An `ItemsSource` on the Object menu would need a `ControlTheme` deriving from Fluent's own MenuItem theme - a mechanism this shell has no other instance of, whose failure mode is a submenu of correctly-sized blank rows, and which the viewport's context menu could not use anyway because it is assembled in code. Both refill on OPEN rather than at construction, since the window outlives every session and entries built once would still offer the first project's classes in the third project's window; the placement differs (the view centre against the right-click point), which is exactly why the entry carries values and not a command.
- **The viewport's input arbitration is a platform-free router, extracted while both hosts were still native.** `ViewportInputRouter` owns the button state, the cursor lock's centre anchor and restore point, the anchor-differencing locked move with its re-pin, the chord table and its stand-down while locked, and the focus-loss path; `IViewportCursor` is the platform half. It names no Win32 and no Avalonia type, so re-hosting the viewport is a sibling adapter rather than a rewrite of logic that **had never been under test at all**, being unreachable without a real HWND and a message pump. Three of its pins exist for failures that are invisible by construction: the cursor clip is released **strictly before** the restore teleport (asserted on call ORDER, because reversing them puts the pointer outside the window), focus loss emits **balanced** button releases (or a button stays down with no event that would ever lift it), and the right-click arbitration measures **net displacement** rather than path length - summing the path made a slow click on a high-DPI mouse silently open no menu while clicking faster fixed it, which is a bug nobody can report. `OnViewportMoved` exists ahead of its caller because a viewport that can be dragged between docks must re-anchor a live lock.
- **A shared render target is the one target that is never resized in place, and `IRenderSurface` gains no member for it.** `RenderTargetSharing` is an enum rather than a bool because a shared fence is the same handshake said differently; `Validate` refuses sharing on a depth-only target and on any colour format but `Rgba8`, since the compositor's external-image import has no half-float path and a request nothing can satisfy must fail where it is made rather than three layers down in a driver. **The identity-survives-a-resize guarantee stops at the handle** - the wrapper surviving is exactly what would let a caller assume the handle did, so a shared target is recreated under a new generation and the old one retired, or the compositor samples a destroyed resource. `RenderSurfaceKind.Composited` is appended and **`IRenderSurface` takes no new member**, deliberately: a convention test's stub implements that interface and is the tripwire for that drift. The key protocol is documented on the producer side - acquire 0 release 1, the consumer mirrored - and an acquire TIMEOUT means the consumer never took its turn, whose correct answer is to skip that frame's shared write, never to block the render thread. **Measured, not assumed** (`--interop-probe`, which now imports real textures rather than reading capability flags): on this machine a D3D11 keyed-mutex NT handle imports and updates, a **D3D12-created handle is refused with `E_NOINTERFACE` inside the compositor's own import**, and a D3D11On12 bridge over the same device works. A capability flag is not proof; a machine can advertise a handle kind it cannot synchronise. **D3D11 implements it now, and building it measured three more things that all fail SILENTLY.** An `_SRGB` RTV over a `_UNORM` shared resource is accepted and does encode (a clear of linear 0.5 reads back 188), which is the double-encode defence the D3D12 back buffer already uses, but the matching `_SRGB` SRV is refused with `E_INVALIDARG`, so the SRV stays UNORM and the asymmetry is deliberate rather than an oversight. A keyed-mutex resource cleared **without holding the key** returns `S_OK`, raises nothing on the debug layer, and writes zeros, so the only evidence of a missing acquire is a black picture: that one is a test now. And `AcquireSync`'s timeout is `WAIT_TIMEOUT` (0x00000102), a **positive** HRESULT, so the ordinary `hr < 0` failure test reads a stalled consumer as success and the frame writes into a texture the compositor is still reading. The mutex bracket wraps the pipeline execute AND the resolve as one hold, because with HDR off the pipeline draws straight into the shared texture and a second bracket would leave that draw outside the key.
  - **D3D12 gets there through the bridge, and its shared texture is D3D11's own code path rather than a second one.** `D3D12On11Bridge` brings a D3D11 front end up over the renderer's OWN device and queue, and the shared keyed-mutex texture is built by `D3D11Texture.CreateRenderTargetTexture` on it - so the UNORM-resource-plus-sRGB-view split, the NT handle and the mutex are one decision in one place, and the two backends cannot disagree about the colour space. The frame lands in an ORDINARY private D3D12 target (`Rgba8` sRGB, no `RenderTargetSharing`, because a D3D12 handle is what the import refuses) and one `CopyResource` per frame carries it across. **The key bracket is therefore narrow here and wide on D3D11**: nothing on the D3D12 side ever touches the shared texture, so the mutex covers only the copy, and the copy is submitted AFTER `ExecuteCommandLists` because the bridge records into the same queue and a queue is already a total order. **`Present` keeps `WaitForGpu()` even with no swap chain to present to** - the upload ring, the mesh buffer pool and the descriptor-heap growth are all gated on that wait and none of them has anything to do with a chain.
  - **The double sRGB encode has a standing detector now, and it is `--viewport-compare`.** The shared route is a UNORM resource wearing an `_SRGB` view on D3D11 and a private sRGB target copied across a bridge on D3D12, and either encoding a second time washes the frame out with **no exception, no HRESULT and nothing on the debug layer** - `--offscreen-probe` counts debug-layer errors and a wrong picture raises none. So `Renderer.CompareTarget` resolves the SAME source into an ordinary `Rgba8` sRGB target beside the shared one, **in the same frame and the same command list** (the shape `ProbeTarget` established, and the reason instance buffers already rewind once per FRAME rather than per pipeline execution), both are read back whole, and `ViewportCompare` reports the max per-channel delta. **Measured: 0 on D3D11 and 0 on D3D12** over 921,600 texels at 1280x720, which is the honest expectation - one shader, one source, two targets of the same format - so the threshold of 2 is a driver-rounding tolerance rather than a number anything is meant to reach, and a double encode arrives at 35 (linear 0.5 stores as 188 and re-encodes to 223). Three things are load-bearing. **The read must go through what a CONSUMER would see** (`Renderer.TryReadSharedPixels`), never through the present target, because on D3D12 the present target is the private D3D12 resource and reading it would measure everything except the bridge's copy - which is exactly where a second encode would live. **The probe stands in for the consumer as well as measuring it**: with nobody importing the handle the producer writes one shared frame and every frame after it skips on `WAIT_TIMEOUT`, so each update takes the consumer's turn (acquire 1, release 0) - and the update that READS must not, because taking the turn twice hands key 0 back before the read asks for key 1 and reports a shared target nobody ever wrote. And **the reference picture is checked for VARIATION first** (`ViewportCompare.HasVariation`), because two blank pictures agree perfectly: a frame that drew nothing would otherwise report the strongest possible PASS. It runs on a **composited surface with no window**, refuses `opengl` by name, and ends the run itself.
  - **`Renderer.ReadTargetPixels` is the plural readback, and the pitch is the driver's.** The singular form creates a staging resource, copies one texel and maps it, which is right for the four corners a diagnostic asks about and is 921,600 device round trips for a frame; every backend now expresses the singular through the plural so there is one staging copy and one row-flip expression each. Two things fail silently in it and are therefore shared in `PixelReadback`: a destination too short is a memcpy past the end of a buffer rather than an exception, and **a row walk that assumes `width * 4` shears the picture by a few texels per row on a driver that pads and is perfectly correct on one that does not** (D3D12's placed footprint is 256-aligned whatever the region asked for; D3D11's staging pitch is whatever the driver chose). The destination's row 0 is the BOTTOM of the picture, the same picture-space contract the singular form states, so the two backends' conventions are converted where they arise rather than leaking into a comparison.
  - **`CreateWrappedResource` raises a debug-layer ERROR per wrap, and it is the one this counter forgives.** `ID3D12CompatibilityDevice::ReflectSharedProperties` reports "Resource provided was not shared by D3D11, or with a D3D11 desc" because a resource D3D12 created has no D3D11 description - which is exactly why the call takes a `D3D11_RESOURCE_FLAGS` to fall back to, and the wrap then succeeds and the pixels arrive. Measured: it **survives `D3D12_HEAP_FLAG_SHARED`**, so it is structural rather than a missing creation option. Counted, it would leave every composited D3D12 session permanently reporting one error in the standing status slot, which teaches people to ignore the only continuous detector a composited surface has; so `DrainDebugMessages` logs it at Debug and does not count it, gated on the bridge existing and on that one `MessageID`, and everything else stays a hard zero. The vtable call itself is the other trap: `ID3D11On12Device` declares CreateWrappedResource, then **Release**, then **Acquire** (slots 3, 4, 5), both of the latter returning void - so reading the slots in call order swaps the bracket, compiles, runs, and reports nothing.
- **`DebugLayerErrorCount` rides the frame snapshot, and it carries whether the layer is RUNNING.** It was read by exactly one thing, the offscreen probe. A composited viewport has no headless gate at all, which makes this counter the only continuous detector of a missing barrier or a mismatched pipeline state, so it publishes to a standing status slot of its own (never the message line, which is last-writer-wins). `DebugLayerActive` travels beside it because **zero-and-off and zero-and-clean are the same number and mean opposite things**, and a gate that quietly weakens is worse than one that fails.

- **The scene graph is the single spine.** Everything lives in it, including brushes (`SceneNode.Brush`).
- **Brushes are the authoring primitive** for static world geometry, Hammer-style: size in the brush's local planes, placement from the node's world transform (keep brush transforms rigid — no scale). Brush-local frames keep CSG precision independent of world position.
- **Two declared bits decide what a brush IS, and neither is ever inherited or derived.** `SceneNode.BrushKind { World, Part }` decides *admission* — whether the brush is fused into the static world at all — and `Brush.Operation { Additive, Subtractive }` decides *sign* — whether it adds solid or removes it. They are independent, they live on different objects for a reason, and both exist because an admission-or-composition predicate computed from mutable ancestry is how silent corruption happens.
  - **`BrushKind` lives on the NODE, is NOT inherited, and has no `Inherit` value.** A `Part` brush leaves the placement list entirely: never carved, carves nothing, draws from its own brush-local mesh under the node's world matrix (`PartBrushMeshCache`), and costs *no* static-world recompile however much it moves. That is the point — the carve is union-skin extraction, so a brush merely *sitting* in the world is harmless, but a brush that **moves under simulation** changes the overlap *set* every tick, which the incremental compiler cannot carry, so it would bail to the fully-validated O(world) compile every tick, forever, while everything still rendered correctly. Non-inheritance is what keeps `AddChild` from being a refusal site and stops any reparent from rewriting world topology. The subtree counter is therefore **two lanes with one private writer**: `SubtreeBrushCount` stays kind-BLIND (rigidity — a scale above a *part* brush is just as illegal, and `ScaleGizmo`'s group refusal reads it), while `SubtreeStaticWorldBrushCount` answers dirtying. A kind flip is the one admission write and goes through `Scene.MarkAdmissionChanged`, which bumps the graph-structure version *as well as* dirtying — a conversion shifts every later placement slot while adding and removing no nodes, so no membership event fires and a stale structure version plus a shifted slot map is a trusted diff applied to the wrong placements.
  - **`Brush.Operation` lives on the immutable BRUSH value**, because it changes the *solid* and must therefore be visible to all three change detectors, which compare `Brush` reference identity and nothing else. The compiled solid is `⋃{additive} \ ⋃{subtractive}`, regularized, **unordered** — never an ordered CSG tree. The only total order over admitted brushes is graph traversal order; today it chooses between two *geometrically identical* coplanar faces, so a reparent is invisible, but under an ordered subtraction it would choose between "there is a doorway here" and "there is a wall here". A subtractive brush emits no skin of its own and instead seeds **cavity walls** (`Polygon.Flipped()` — winding and plane negated in one expression, the only reversal primitive in the engine) into each brush it cuts, attributed to the **cut** brush's slot — which is why chunk ownership, weld candidate sets and render bounds need no formula changes and the whole downstream pipeline is untouched. Subtractive carvers use `Polygon.Split`'s own per-vertex classification, **never `Csg.CoplanarOrientation`** (ten times looser in offset; the gap opens a ring around every cavity mouth). `WithFaceSurface` and `WithScaledExtents` must thread `Operation` through, or **retexturing or resizing a hole turns it into a solid block**.
  - **Both render nothing by default and must be drawn by the editor**, in `SpectraEngine.Editing` so a shipped game never links it: part brushes cyan, subtractive brushes magenta with an inward tick per face. A part and a world brush are otherwise indistinguishable at rest yet interpenetrate instead of merging and z-fight on coplanar faces; a subtractive brush is invisible *and* unpickable while deleting the level. Both overlays disclose their per-frame cap rather than silently truncating.
- **`Scene.StaticWorld`/`StaticWorldChunkMeshes` are derived data**, never authored — and the recompile is async: brush-node edits auto-mark the world dirty (transform/brush setters via the node's `Owner` scene), the render thread snapshots `BrushPlacement`s (validating rigidity), a background task runs the pure-CPU compile (carve → snap → weld → per-cell BSP → per-cell mesh arrays split per face material, each stage reusing carried caches), and the render thread swaps the result in when it lands — creating GPU meshes per (chunk, material) only for the chunks whose artifacts changed and destroying only the replaced/removed ones (`Scene.ProcessStaticWorldCompilation`, one compile in flight, progressive results while dragging). `Scene.RebuildStaticWorld` stays as the synchronous (cache-free) path for load time and tests. The world renders through `RenderView.WorldItems`: culling stays per chunk against each chunk's true render AABB (owned surfaces can overhang the cell), and a surviving chunk emits one item per material it wears, with the material resolved from the compiled `MaterialRef` at swap time through `Scene.Assets` (`Scene.StaticWorldMaterial` is the fallback for faces that name none).
- **BSP is a query structure only** (ContainsPoint/Raycast, future collision traces) — never the render path — and per-cell: point queries route to the containing chunk's tree (`CsgWorld.ContainsPoint`), rays walk the occupied cells front-to-back with a 3D-DDA (`CsgWorld.Raycast`), with answers identical to a monolithic tree. No PVS/portals; culling is a scene-level system — frustum + BVH over the scene's spatial nodes (`SceneBvh`), plus a per-chunk render-AABB pass for the static world.
- **Not a Source-style sealed-BSP engine — open world is first-class, and the chunked pipeline is implemented end to end, incremental compile included.** Brushes are placed like Roblox "parts": freely, anywhere, in an unbounded world. Never introduce sealed-world requirements, leaks-as-blockers, PVS, or map extents. Brush-local frames make precision position-independent, and the static world is chunked: a sparse 32-unit cell grid (`ChunkCoord`/`ChunkGrid` — dictionary-keyed and layered, so negative and distant cells cost the same as the origin), per-cell weld/BSP/mesh, dirty-cell-only recompiles and GPU swaps, chunk-culled rendering, and queries routed point→cell / ray→DDA. Steady-state edits compile through the incremental previous-world path (`CsgWorld.Build(placements, dirtyCells, previousWorld)` → `CsgIncrementalCompiler`): the scene hands each background compile the last landed world, and the compile re-runs only the edit's neighbourhood — paged copy-on-write carry (`CsgWorldCarry`/`PagedArray`), fresh chunks only for affected cells, classic validation caches derived lazily for the fallback path — so NO per-edit cost scales with the world (structural edits — count/order changes, new overlap pairs — fall back to the fully validated compile for that one recompile). The CsgBench `openworld` scenario (1k/10k/50k scattered parts, half around +8,000 units) guards the pillar: a one-part edit costs ~0.05–0.1 ms at every world size (Aug 2026), and its verdict line must say "world-size independent". Brush *resizing* edits local plane extents (parts-like), never node scale.
- **Editing lives above the engine, behind two seams, in its own assembly.** (1) *Input:* editor tools consume an immutable `EditorInputFrame` (cursor in viewport pixels, viewport size, button state + press/release edges, modifiers, scroll, dt) built by an `IEditorInputSource`; nothing in `SpectraEngine.Editing` may name a Silk.NET type or `IWindow`, so re-hosting the viewport in Uno means writing a sibling of `EngineEditorInputSource`, not touching a tool. Core carries the backend-neutral vocabulary (`PointerButtons`, `KeyModifiers`, `Renderer.GetFramebufferSize`) that makes that possible. (2) *Edits:* every scene change goes through an `IEditorCommand` that **addresses nodes by `SceneNode.Id`, not by reference** (undo of a delete recreates the node under the same id — `new SceneNode(name, id)` — so references go stale) and **captures absolute before/after values, never deltas or scene snapshots** (the transform setters early-out on exact equality and the CSG caches key on exact values, so replaying an absolute value is idempotent and free). `Scene.TryFindById` is the id index that resolves them, maintained from `NodeAdded`/`NodeRemoved`. A whole gizmo drag is ONE undo entry via an `UndoStack` transaction: begin on grab, per-frame commands coalesce into the open transaction (`ICoalescingCommand`), commit on release, cancel rolls back. History is a bounded ring; any new command invalidates redo. Render-thread-only throughout, like the scene it edits.
- **One gizmo spine, three tools.** `GizmoTool` owns everything the manipulators share — the pivot and frame, the constant-screen-size `GizmoGeometry`, the hit test → grab → drag → commit/cancel state machine, the one-transaction-per-gesture undo, the `GizmoDragTarget` capture — and each tool supplies only four hooks (hit test, prepare drag, apply drag, draw). **Every drag frame recomputes its result from the grab capture, never from the previous frame**, so rounding and snapping leave no residue and a cancel restores exactly; the rotate winding number is the sole deliberate exception (a cursor defines its angle only modulo a turn). Snapping is one policy (`SnapSettings`: enabled, ladder, Alt inverts per gesture) over three units, and **all three are absolute quantities of the thing being edited, never a multiplier** — world-unit position (1, presets 0.25/0.5/1/2/4), degrees (15, presets 5/15/45/90), world-unit *size* (1, the same ladder as the move grid but a separate `ResizeSnapSettings` instance so a UI can link or split them). **A resize snaps the resulting size, not the scale factor**: quantising the factor made the world-space step proportional to whatever the object already measured (at 0.25, a 10-unit brush jumped 2.5 units per notch and a 0.4-unit brush 0.1), so the tool now takes the cursor's travel along the constraint as the size change 1:1 in world units and *derives* each node's factor from its own measured size (`ResizeMath`) — one notch is one increment on every object in the selection, at any size. Size is measured from brush plane bounds or from mesh bounds × world scale (one definition, `GizmoSelectionBounds.TryGetLocalBounds`, shared with the box the Studio handles stand on, so a node cannot be big enough to put a handle on and too small to resize); a node with neither (an empty group, a mesh reporting no bounds) is the only case that still drags proportionally, and it says so through `ScaleGizmo.ProportionalFallbackCount` and a log line rather than silently. **What a resize holds still is the STYLE's decision, and the handle roster travels with it** (see the switchable-styles bullet below): face-anchored under Studio, symmetric about the pivot under Classic, with `ScaleGizmo.SymmetricModifier` (Shift) asking for the other one for a gesture. The uniform centre cube is always symmetric and grows the largest dimension by the increment. **Translate and rotate honour a world/local frame toggle; scale does not** — a non-uniform scale is only defined in the scaled object's own axes, so `ScaleGizmo` is local-only. **And the scale gizmo never writes node scale on a brush node**: it rebuilds the brush through `Brush.WithScaledExtents` (the exact half-space image of the solid under a diagonal map, so wedges work too) and swaps the successor on via `SetBrushCommand`, which is also what invalidates that brush's cached carve; the anchoring shift rides a `SetLocalTransformCommand` that writes *position only*, which keeps the placement rigid. Default keys, resolved by name through `GizmoShortcuts` so the assembly still names no key enum: **W/E/R = move/rotate/resize** (the Unity/Unreal row) and **2/3/4 = move/resize/rotate** (the Roblox Studio row, whose order is Studio's own and deliberately NOT the same as W/E/R's), X for world↔local, Y for Studio↔Classic handles, G and `[`/`]` for snap.
- **The handle roster and the resize anchoring are ONE decision, and that decision is `GizmoStyle`.** The engine shipped Studio's semantics (a resize plants the face opposite the handle) on Blender's roster (handles on the positive ends only), and those two do not compose: with nothing to grab on the −x side, three of every object's six faces were unreachable and "grow this leftwards" had no gesture at all. `GizmoHandle` therefore carries six axis values (`AxisNegX`/`Y`/`Z`, laid out contiguously after the positive three so `IsAxis` stays a range test), and a style names which of them exist. **`GizmoStyle.Studio` is the default**: six per-face handles standing on the selection's own box, a pivot at that box's centre, a face-anchored resize, no plane quads and no view ring. **`GizmoStyle.Classic`** is the Blender/Unity layout: three handles at a fixed distance from the pivot, plane quads, a view ring, a pivot at the average of the selected origins, and a resize symmetric about the pivot, which is exactly why three handles are enough there. **It is data, not a strategy object, and there is still one `Pick` and one `Draw` per tool**: everything that varies turned out to be a flag, a number or an enum, so the renderers and hit testers read the roster from the same `GizmoGeometry` and cannot disagree about it per style. Two load-bearing details. **A sign belongs in the travel, never in the axis mask**: `ScaleGizmo` masks by the handle's AXIS (`GizmoHandles.PositiveAxis`), because reading the raw handle drops the negative values into the mask table's uniform default and turns every negative-face drag into a silent three-axis resize that throws nothing and logs nothing. And **`GizmoGeometry` separates where a handle STANDS from how big it IS**: the size stays a screen-space constant, while the reach is per direction (`PositiveReach`/`NegativeReach`, floored by `MinimumReachFactor` so a tiny or flat object still gets handles you can aim at) because the two ends of an axis stop being equidistant from the pivot the moment a face-anchored resize starts pushing geometry out from under it.
- **A UI thread never touches the engine; it posts work and reads values.** `EngineHost` (`Engine.Host`) is the entire surface: `EnqueueCommand(Action<Scene>)`, `RequestShutdown()`, and a `FrameCompleted` event carrying an immutable `FrameSnapshot`. The render thread keeps owning the graphics context, every scene mutation and all GPU resource creation, which is what lets the async CSG pipeline, the BVH, the selection set and the undo stack keep their single-threaded proofs verbatim. **Where the two calls sit is load-bearing**: commands drain immediately BEFORE the static-world compile pump, so an edit and the recompile it causes land in the same frame rather than a frame apart, and snapshots publish AFTER Present, so a snapshot describes a finished frame and a handler's cost can only delay the next one. **Snapshots go out on an interval (~30 Hz), never per frame** (the engine runs at hundreds of frames a second and no panel refreshes that fast, so per-frame publishing would be real render-thread garbage for a UI that discards it) but **structural changes are never dropped by that**: `SceneChangeLog` accumulates continuously, every change rides the next snapshot, and a frame carrying changes publishes regardless of the clock. **Nothing crossing the boundary is a live object**: ids and names, never a `SceneNode`, because a node belongs to the render thread and will be mutated again the instant the frame ends. **`Scene.NodeReparented` exists because a reparent within one scene raises NEITHER membership event** (nothing entered or left the graph), so a tree view fed only `NodeAdded`/`NodeRemoved` desynchronises the first time somebody drags a node in it. The log reports overflow rather than truncating, for the same reason everything else here does: a view fed a partial change list looks correct and is wrong. `SubmitInput` is the fourth member and arrived a milestone later than the rest, once a real shell existed to shape it (see the input bullet below). **A UI DRIVES the editor through the same verbs a key chord uses** (`SceneEditorHost.Apply`, `EditorHostCommand`), never by synthesising key presses: that would be a second input path free to drift, and it would not even work, because the letter-row bindings deliberately stand down while a camera is driving.
- **The engine runs without a window, and `Engine.Start(IRenderSurface)` is the whole of that.** `Run()` still creates a window, pumps its events and blocks until it closes; `Start`/`Stop` take a surface somebody else owns, start the same render thread against it and return immediately. **They are deliberately not one call**, because blocking is what owning the process's main loop MEANS and a shell calling from its UI thread has to get control back. Everything the standalone path does with its window stays with the caller: the title, the cursor, the event pump, the close button and the fullscreen transition are all things a shell already owns. **Nothing about fullscreen is dropped by that** and nothing needed changing either: `IWindowModeLatch` was already a request latch read by whoever owns the window, so an embedded host polls `RequestedWindowMode` exactly as `Run`'s pump does. The exit flags are cleared at START rather than at the end of a run, so `Stop`'s return value and `Faulted` still describe the session that just ended while a restart cannot inherit a raised `_closeRequested` and exit before its first frame.
- **Input has one state machine and two ways in, and `InputKey` is what made that possible.** The engine's input state used to store `Silk.NET.Input.Key`, which quietly made a windowing backend the vocabulary every consumer named, so a shell feeding the engine would have had to reference the backend of a window it does not own purely to say "the user pressed W". Core now owns `InputKey`/`InputEvent`, `InputManager` stores those, and **the standalone window's own device callbacks are submissions too** (`SilkInputKeys` is the one adapter, and its hundred hand-written pairs are checked by NAME rather than by eye, because a transposition in that table is invisible: the wrong key simply stops working). Edge detection, the auto-repeat filter, the delta accumulator and the focus-loss release are therefore one implementation, so an embedded viewport cannot drift from the standalone window in how a press or a drag behaves. Three details are load-bearing. **An absolute pointer position and a raw delta are separate event kinds**, because a captured cursor has no meaningful position at all (the OS reports one that walks away from the window as you look around) and collapsing them is how a freelook ends up computing its motion from a coordinate that stopped meaning anything. **`InputKey.Unknown` never enters the held set**: every key the engine has no name for arrives as that one value, so admitting them would make them a single shared entry and one release would lift them all. And **the cursor is a request the HOST applies**: an embedded engine has no device to hide, so it publishes `EngineHost.RequestedCursorMode`, the shell performs the platform capture it alone can, and `ApplyPendingCursorMode` closes the state machine, which works only because the bookkeeping half of that method already ran with or without a device.

- **There is a second host, and it is `SpectraEngine.Editor`: an Avalonia shell with the engine running live in a docked pane.** It is a PEER of the demo executable, not a layer above it: it builds the renderer, the managers and the editor through the same factories and calls `Engine.Start` instead of `Engine.Run`. **The viewport is a real Win32 child window the shell creates itself**, with the engine's swap chain behind it and its own render thread, so no part of the frame goes through the UI framework. Creating the window rather than taking Avalonia's default one is load-bearing: **a native child is where the OS delivers the mouse**, its messages go to its own window procedure and do NOT bubble to the parent, so a viewport hosted on somebody else's child renders perfectly and never responds to a click. Owning the class also owns `CS_OWNDC`, which the embedded GL context will need. **The cursor is the shell's**, since an embedded engine has no device to hide: it pins the pointer at the viewport's CENTRE while looking (an edge anchor loses half the travel before the teleport catches it) and restores it to where the press happened, then closes the engine's state machine with `ApplyPendingCursorMode`. **The airspace cost is real and accepted for v1, and it is narrower than it was first written**: nothing Avalonia draws INTO THIS WINDOW may cross the viewport - an overlay, an adorner, a drop shadow, a dock float in the managed layer. A POPUP is a different thing, and this was measured rather than reasoned about: on Windows an Avalonia popup is a real OS window, so context menus, menu flyouts, combo dropdowns, tooltips and modal dialogs all composite ABOVE the native child (proven with a screen capture of a tree row's context menu opening 300px out over live 3D). `H3`'s composition path exists to remove what remains. **`opengl` is refused by name rather than attempted**, because an embedded GL surface needs its own WGL context and proc-address loader; letting the renderer discover that would report it as a driver failure.
- **`--interop-probe` answers the one question that gates replacing the viewport's native child, and it MEASURES rather than reasons.** The viewport is a real Win32 child, which composites above everything Avalonia draws and is the single fact behind every layout limit the shell has: no overlays over the 3D view, no split views, no dockable viewport, no drag-and-drop into the scene. Replacing it means handing the compositor a texture the engine rendered, and whether that is possible at all is a per-DRIVER fact - Avalonia's Windows interop is ANGLE, GL ES over D3D11, so whether it accepts a D3D12-created handle is not something to guess at. The probe opens a real window (there is no headless form of the question: the compositor is created by the platform when a top level exists, and the interop is negotiated with the render backend that window is attached to), asks `Compositor.TryGetCompositionGpuInterop`, and prints the adapter LUID, every `SupportedImageHandleTypes` entry and `GetSynchronizationCapabilities` for each - **per handle kind, not per device, because a machine can accept a handle it cannot synchronise with a keyed mutex**, which is exactly the case that would decide between importing a D3D12 handle directly and bridging through D3D11On12. **Measured here: both `D3D11TextureGlobalSharedHandle` and `D3D11TextureNtHandle` import, both with `KeyedMutex`** - the best available answer, and what `UpdateWithKeyedMutexAsync` wants. It runs INSTEAD of opening a session and closes itself, because it is a measurement of the machine rather than a feature and must not compete with an engine session for the GPU while it asks; and it catches its own failure, because it runs on a machine whose driver is exactly the unknown being measured.

- **The shell opens and saves maps, and the split is UI thread for the FILES, render thread for the SCENE.** A bundle is ordinary file I/O and belongs where the dialogs are; the graph, the static-world compile and every GPU resource belong to the thread that owns the frame, so `EditorSession.OpenMap`/`SaveMap`/`NewMap` do the work inside `EnqueueCommand` and hand the result back through a callback the caller has to marshal deliberately. **Opening resets the editor first via `SceneEditorHost.OnSceneReplaced`**, and all three parts of that fail silently on their own: an open gesture is manipulating nodes about to leave the graph, the selection holds live `SceneNode` references that would outlive their scene, and the history addresses the old graph by id, where `IEditorCommand.Undo` **no-ops on a missing target** rather than failing, so Ctrl+Z would simply do nothing. It is deliberately NOT an `EditorHostCommand`: every other way a UI drives the editor is a verb a key chord also uses, and no user presses "the scene was replaced".
  - **Ctrl+S works in the viewport only because the viewport gives it up.** The viewport is a native child window, so while it has focus the OS delivers the keyboard there and Avalonia's menu accelerators never fire at all - which for Ctrl+S is the worst possible failure, since it is the chord people press without looking and trust to have worked. The window procedure intercepts a short, closed list of Ctrl chords (`ShellChord`) and raises them instead of submitting them to the engine. **Only DOCUMENT verbs are on that list**; anything about the scene stays with the engine keymap, which already knows whether a camera is driving. `GetKeyState`, not `GetAsyncKeyState`: the async form reports the keyboard as of now rather than as of the message, so a quickly released modifier is lost.
  - **The pickers ask for FOLDERS, and a modal window is the one thing allowed over the viewport.** A map bundle is a directory, so "save as" is a folder picker plus a name dialog rather than a save-file dialog: pointing one of those at a bundle means either lying about what is being created or depending on whether a backend touches the path it returns. `NameDialog` is a real top-level window, which is why it may sit over the viewport when nothing drawn inside the shell can - the airspace rule is about Avalonia's own surface, not about modality. **The File dropdown falls over the 280-wide tree column**, which is why it works at all; anything wider has to become a modal.
  - **Dirty tracking follows any movement of the undo history and errs toward dirty.** Depth alone cannot do better: undo one entry, make a different edit, and the depth is back where it started with different content behind it. The history is the right signal because it is the only thing that moves for an edit and stays still for everything else - the demo scene animates a brush and recompiles the world hundreds of times a second without touching a command. **Discarding unsaved work asks for a TYPED confirmation**, because it is the one dialog whose wrong answer destroys work that cannot be recovered: the undo history goes with the scene.
- **The editor has a property panel, and the whole design is one decision: which properties exist is DERIVED, never authored.** `NodeInspector` turns a node into `PropertyRow` values whose `Group` is the payload the value came from, so a node carrying a light grows a Light section and one that does not simply has no such rows. `PropertyId` is an **enum rather than a string key**, which is what keeps it AOT-safe: the obvious property grid reflects over an object to discover its members, and trimming removes what only reflection names. `PropertyKind` is a small closed vocabulary so the panel renders one editor per kind and a future component gets an editor for free; it is the same vocabulary `D16`'s entity panel will need.
  - **A multi-selection shows the UNION, and mixing is tracked per AXIS.** Hiding a row because only part of the selection carries it would mean selecting one extra object silently removes the field somebody was about to type into, so such rows are shown, labelled `3 of 5`, and edited as a bulk edit over the nodes that have it. **Per axis is the consequential part**: "put all of these on the floor" sets y and must leave x and z alone, so a vector row is three cells each committing with its own mask, and a row that could only report "these differ" and write all three back would be a way to stack the selection at one point. Comparison is **exact, never tolerant** - two positions differing by an ulp really are different, and a tolerance would report them settled and then write one over the other. Merge order is `PropertyId`'s declaration order, which is deliberately the display order, so a light-plus-brush selection lays out the same whichever was clicked first and every group stays one contiguous run.
  - **A commit is Enter or losing focus, and every rule follows from that.** One commit is ONE transaction, so a bulk edit over fifty objects is one Ctrl+Z; a node already holding the value records nothing, because tabbing through fields is ordinary and would otherwise fill the history with entries that undo to themselves. **A focused field stops taking refreshes** - a gizmo drag republishes at the snapshot rate and a field that took each one would delete characters as they are typed, which reads as a broken keyboard. **Escape reverts, and exists precisely BECAUSE blur commits**, or a half-typed value could never be abandoned. Unparseable text reverts rather than sticking. **Enter commits and STOPS editing**: it used to call `BeginEdit()` again straight afterwards, on the reasoning that focus stays in the box so the edit is still open, and the effect was that the field never took another refresh for as long as it kept focus - type a position, press Enter, then drag the object in the viewport, and the box went on showing the number you typed while the object was somewhere else. A field that lies about where an object is is worse than one that loses focus. A checkbox and a dropdown apply on the click (there is no typing to finish) and **guard their refresh**, since assigning the published value back looks exactly like a click.
  - **Rotation is euler degrees, which is a lossy VIEW of an exact value**, and `EulerAngles` follows `Quaternion.CreateFromYawPitchRoll` because three call sites already write rotations that way; a different order would make an angle typed into the panel disagree with the same angle written in code. The round trip is exact in **rotation, not in numbers** (euler triples are three-to-one, and at pitch +/-90 only yaw+roll survives), so the tests compare where basis vectors land rather than components, which also dodges the `q == -q` double cover. A bulk rotate merges **in degrees**, since a quaternion has no separable components to leave alone. **A brush row shows SIZE, not planes**: planes are the truth and nobody types them, bounds are what the resize gesture already works in, and one typed number is then the same world measurement on every object whatever each already measured.
  - **Values the payload would refuse are refused before anything is written.** `Light`'s setters throw rather than clamp (range must be strictly positive, intensity rejects negatives and NaN), so a command carrying one would throw from inside `Do` halfway through a transaction, leaving the history open and the scene half-edited; clamping instead would write a number nobody asked for and report nothing. **`SetLightCommand` captures VALUES, not the light**, because `Light` is the one mutable payload and restoring a pointer would restore an object the redo had already overwritten, so undo would appear to do nothing.
  - **The panel names its subject, and a number can be DRAGGED.** Those two changes are what separate an editor's inspector from a settings dialog. The **name is the panel's header** - an editable title with a derived kind chip beside it (Block / Part / Cut / Light / Mesh, read off which sections the selection grew) - rather than the first row of a "Node" section whose other row was a permanently truncated GUID. That section spent the two most valuable rows in the panel on a duplicate and an identifier nobody can use; the id is still what every command addresses and is simply not a thing to look at. Skipping published rows means the model's rows and the snapshot's are no longer index-for-index, so each row carries its `SourceIndex` and `SameShape` compares against the PUBLISHED shape - comparing the two directly reports a mismatch on every publish and rebuilds the panel thirty times a second, resetting scroll and dropping focus as it goes.
  - **A vector row is TWO LINES, because one does not fit.** At the panel's 308px a fixed label column plus three cells side by side left about 31px of interior per cell - five characters of monospace - so `-125.5` could not be displayed at all, in a panel whose main job is displaying positions. Label and unit take one line, the three cells take the next, and each cell is then wide enough for a real number. **The axis letter is a HANDLE, not a decoration**, and it wears the same hue its arrow wears in the viewport (`GizmoColors`, desaturated: at panel scale the full-strength values read as three more accents and #FF4040 is close enough to the brand red to be mistaken for a selection). Pressing it and moving sideways writes the value continuously; pressing the row's label drags all three. Shift is ten times, Ctrl a tenth, releasing without travel is a click rather than a drag, losing the pointer cancels, a press that is not the LEFT button is ignored (Avalonia raises `PointerPressed` for every button and a capture is per pointer, so a right-press on its way to a context menu would otherwise open a transaction and write positions for as long as it was held), and a mixed cell refuses the gesture because an absolute write would silently collapse the whole selection onto one number. **A label drag is a uniform DELTA over each cell's own captured start, never one shared absolute value** - the commands are absolute by design, so seeding all three axes from x and writing that back does not offset y and z, it overwrites them: a position of (10, 2, -5) becomes (10.02, 10.02, 10.02) on the first pointer move, and a brush of any shape becomes a cube. **Typing and scrubbing need SEPARATE guards on the field**, because a vector drag ends by releasing the guard on all three cells: with one flag, a cell somebody had typed into and not committed was handed back to the refresh by a drag on its neighbour and silently overwritten on the next publish. A pointer capture does not move keyboard focus, so the two states are genuinely independent.
  - **A drag is ONE undo entry, through `SceneEditorHost.BeginPropertyGesture`/`EndPropertyGesture`.** The host holds a transaction open around the gesture and `PropertyEditor.Apply(..., inGesture: true)` joins it instead of opening its own, so the coalescing commands inside keep the value the drag STARTED from. Without it a sixty-frame drag is sixty history entries and "put it back" is sixty presses. Cancelling rolls back rather than merely stopping, or an abandoned drag leaves the scene holding whatever number the pointer last passed over with no entry to take it back. **`RefuseEdit` gates on an open gesture too**, with the gesture's own edits exempt: a pointer capture does not block the keyboard, so Ctrl+1 during a drag would insert a block INTO the drag's transaction, and a release without travel cancels that transaction and rolls the insert back - the object appears, is selected, and vanishes, with no history entry and no message.
  - **A colour is a swatch and an sRGB hex, never three linear floats.** A light's colour was rendered as `1, 0.9114, 0.7484` under a label reading "Color (linear)", which is a correct description of the storage and tells a person nothing. The conversion happens at the edge, exactly as it does on the way into a texture. **The hex box is a real cell on the panel's commit contract**, not a string bound straight to a parse-or-revert setter: a two-way `Text` binding writes per keystroke, and "#8", "#80" and "#808" are all unreadable, so every character reverted the box to the last good colour and the value could never be assembled by typing at all (reproduced against Avalonia 12.1.1, not reasoned about). **Units ride the `PropertyRow`** (`su`, `deg`) rather than being derived in the shell, because a unit is a fact about the value and the second consumer would derive it slightly differently.
  - **A brush node has NO editable scale row.** Offering one was a way to stop the level compiling: a brush placement must stay rigid, so a non-rigid world matrix makes every later placement snapshot defective and the static world stops recompiling for the rest of the session while the viewport goes on showing the last good one - a level that silently stops responding to edits, with the reason in a log file. The row is absent (`NodeInspector`), `PropertyEditor` refuses the edit anyway (two guards, because one protects against a UI that could grow the row back and the other against any caller at all), and `Scene.StaticWorldDefect` is published on the snapshot and shown in the status bar as a standing warning in its own slot - not on the message line, which is last-writer-wins and would lose it to the next thing that happens.
  - **Rows ride the `FrameSnapshot`, and the panel is patched rather than replaced.** On the snapshot is what makes the panel follow a gizmo drag; fetched on demand it would show the position the object had before it was picked up. Assigning a fresh collection per publish would reset scroll, drop focus and destroy a half-typed value at the publish rate, so rows are matched by `PropertyId` and reused. **The panel says which property and which value; which NODES that means is the editor's answer**, given on the render thread when the edit runs, because a UI's view of the selection is a frame or two behind.
- **The shell has a look, and the one thing it deliberately does NOT copy from the website is the fake window chrome.** Tokens live in `Theme/Tokens.axaml` and nothing outside it writes a literal colour, size, radius or duration. **The ground is a mid-dark seven-step elevation scale, and moving it off near-black is the change that settled "the look does not feel right".** The shell shipped at `#0A0708` to `#1B1819`: four surfaces separated by 1.06:1, with the 1px borders carrying the entire layout. That palette was designed *against itself* - every ratio inside the chrome was correct - and what was never in the frame was the **viewport**, the only large bright field in the window and the thing the eye actually adapts to. Adapted to a render whose baseplate sits around L\* 65, near-black chrome is a ~25:1 slam and every state change in it lands in the crushed bottom of the response curve, which is exactly why the design looked right in a screenshot (no adapting field) and dead on a monitor. Unreal, Unity, Godot and Blender all sit at L\* 15 to 33 for this reason: the chrome must be quieter than the picture, not a different medium from it. So: window `#131011`, chrome `#1A1718` (the menu, command and status bars, deliberately BELOW the panels so content is the brightest thing), panel `#242021`, raised `#2E2A2B`, control `#383335`, hover `#433D3F`, active `#4E4749`, input `#161314`. Warm-neutral rather than the blue-grey most DCC tools use, because a warm accent on a cool ground is the gamer-RGB look - and at L\* 4 the old palette's documented warmth was below threshold and rendered as neutral black anyway, since hue needs value to show. **Borders became trim rather than scaffolding** and are now LIGHTER than the surface they edge (a highlight edge, which is what a raised control's rim is), where before they were darker because at L\* 4 there was nowhere below to go and every edge in the window was therefore a gap. **The transient hover fills went UP with the ground and had to**: a 4.5% white lift is a fixed absolute delta, and by Weber's law a fixed delta reads as LESS change on a lighter ground, so carrying the old numbers over would have made every hover in the window quieter than before. Explicit text COLOURS rather than opacity on white (opacity breaks Windows subpixel gamma), with muted raised to 4.8:1 because it was 4.3:1 and carrying the inspector's section headings. **A filled red button uses `#C82F30`, not the brand `#E8474A`**, because white on the brand red is 4.0:1 and fails AA at 13px. **Surfaces have a DIRECTION, and the direction is the affordance**: anything you press is lighter than the panel it sits on, anything you type into is darker.
  - **The accent is SELECTION and nothing else, and splitting the other meanings off it is what stopped the window reading as monochrome-plus-one.** Red used to mean selected, live tool, focus, primary, error, drop target and no-match at once, so "you picked this thing" and "the machine is in this mode" were the same signal. Now: `SpectraAccent` is selection (rows, the 2px bar, drop indicators, focus, the one primary button); **`SpectraMode` `#E5A93F` is STATE** (the live gizmo tool, snap on, the dirty dot, a chip showing a non-default value); `SpectraTextDanger` is error TEXT, because the accent as text is 4.0:1 on the panel and that is not an error message. **Warning is the same amber as Mode deliberately, not a second one** - a warning and a lit mode are one family, attention rather than error, and two ambers four degrees apart is a distinction nobody can make; a warning is told apart by its icon and its place. **And the node-kind tints finally get spent**: they existed from the first pass and appeared in exactly one place, a 15px tree glyph, which is why four insert buttons in a row read as four grey outlines.
  - **Every brush is a `SolidColorBrush` over a `DynamicResource` colour, and the consumers keep `StaticResource`.** That is the cheap half of `H4`'s theming item and it is strictly better than the expensive one: swapping the Colors re-tints every brush IN PLACE, so a reference held anywhere else stays correct by construction. Converting all ~380 consumer references to `DynamicResource` buys the same thing and costs a live subscription per reference. **The alias form `<StaticResource ResourceKey=...>` in `DockTokens.axaml` resolves once and caches**, so a future theme swap will not reach Dock's chrome until those are rewritten as brushes over dynamic colours - written down here because nothing fails when it is missed. **Sizes stay static**: a theme that changes the type scale or the row height re-layouts the window and is a different feature.
  - **Section headings are body size and sentence case**, not 10px letter-spaced uppercase. That is the marketing eyebrow, it is the single most web-flavoured move left in the shell, and uppercase is measurably slower to read because it destroys the word shape a reader recognises before reading any letters. "Transform" beats "T R A N S F O R M".
  - **Two defects the rewrite found**: `Border.segsep`'s `Background` and one `BorderBrush` were assigned a `Color` resource rather than a brush, so the segment separators inside every command-bar cluster had never rendered; and `DarkCaption`'s three DWM colours were transcribed hex, which is the one place the theme cannot reach through a brush, so they now READ the token dictionary and a palette move cannot leave the title bar behind. Before that rule existed a mode chip and a text field shared a fill, a border, a radius and a font and differed only by four pixels of height, so two buttons sat in the toolbar dressed as inputs beside three real inputs and nothing on screen said which was which. Raised means press, sunken means type, and there is no third reading to learn. **`SystemAccentColor` is overridden too**: Fluent resolves it from Windows personalisation, so every stock control the shell has not explicitly restyled paints itself in whatever colour the user picked for their taskbar - the pipeline dropdown's selected row was arriving lavender. Naming the family means the next leak leaks brand red instead of somebody's wallpaper. **The site's card motif is refused everywhere in the shell, panel headers included** - it shipped there once (an accent chip plus a monospace pseudo-name, `scene.tree`) and was pulled on direct feedback: code-flavoured identifiers as labels read as confusing decoration, so labels are plain words, mono is reserved for VALUES, and where the dock chrome already names a panel the internal header is gone entirely with its counts moved to where they work (the tree count onto the filter row). A dead minimise/maximise/close trio is refused for the same reason it always was: controls that do nothing teach within one session that this app's controls are decorative. **No custom title bar either** - `DarkCaption` writes three DWM attributes, which gets the colour with none of the hit-testing, Aero Snap or maximised-inset cost, and simply does nothing on an OS that predates them. **A two-way choice is a mono chip showing its current value** (`world` / `Studio`), never a lit icon, because "world" is not the enabled state of "local". **A list is a list, not a grid of cards**: bordered rounded tiles per entry (recents, maps) were pulled on the same feedback the card motif was, because they cost three times the height of a row, carry no more information, and are the single thing that makes a desktop tool read as a web page. Rows are flat, dense, hover-filled and the same idiom everywhere - the scene tree, the maps pane and the launcher's recents all look like the same product. **The start page lays out like the rest of the tool** for the same reason: full-bleed columns with a verb rail and a keyboard-navigable list, not a centred hero with call-to-action buttons, and no header of its own because the window's own bar is directly above it and already carries the File menu (identity moves into that bar's right end while no session is open).
- **Icons share one grid and one draw call, and `Stretch="Uniform"` was quietly destroying both.** `Theme/Icons.axaml` always claimed its glyphs were authored in a common 16x16 box, and they were - but `Path` drew them with `Stretch="Uniform"`, which normalises each geometry to ITS OWN ink bounds and throws the shared grid away. Move rendered at 1.33x, Resize at 1.60x, Play at 1.78x and Stop at 2.29x, so the play button's glyph grew 29% the moment a run started, and eleven unlabelled outlines at four different optical sizes were not eleven icons, they were a grey texture. That is the mechanical cause of the "wall of identical glyphs" complaint. The fix is both halves: every glyph is renormalised so its ink fills 2.5..13.5 on both axes, and `Path.icon` draws with `Stretch="None"` plus one shared `scale(1.2)` render transform - shared, because a per-glyph correction is `Uniform` again under another name. **Kinds are told apart by SILHOUETTE, never by interior strokes**: at 16px with a 1.5 stroke, two shapes with the same outline and different insides are the same shape, which is what the three brush kinds were. They are now a cube on a ground line (a block, fused into the level), a free cube (a part) and a cube with a hole through it (a cut). Fill is allowed in exactly one place, the play/stop pair, whose two glyphs are drawn to the same optical area so the button does not change weight.
- **The shell has a motion system, and it exists because it had NONE.** `Transitions`, `Animation`, `KeyFrame` and `Easing` across `SpectraEngine.Editor` and `SpectraEngine.Editing`: zero occurrences. Every state in the application was a single-frame swap, and that matters twice over - the second reason being the one that gets missed. **A small value step delivered instantly is a step function with no transient, and peripheral vision is motion-driven**: the same step delivered over 90ms is an event you notice without looking at it, so raising the hover fills without adding the ramp would have fixed half the problem. Durations and easings are tokens (`SpectraMotionExit/Fast/Base/Swap`, `SpectraEaseOut/InOut`). **The budget, so this cannot drift into bouncy**: interaction motion is at most 130ms, exactly two non-interaction transitions may exceed it because neither answers a pointer, nothing overshoots (`BackEase`, `BounceEase` and `ElasticEase` are banned by name), and nothing loops or idles. **Nothing on the drag path animates**: a transition on a value a pointer writes every frame is a lag machine, because the target moves before the interpolation lands and the element trails the cursor by exactly the duration - the drop indicators, every property value cell, the status readouts and the rename box are named exclusions, which is why the tree row animates its FILL and not its BORDER (the border is the drop indicator). **Enter and exit share one duration**, and that is a concession rather than a preference: expressing a faster exit means re-declaring the `Transitions` setter inside `:pointerover` and relying on the order Avalonia applies and REVERTS setters when a style frame deactivates, which is not a guarantee it makes - a 55ms exit that is sometimes 90 is a coin flip, not a choice. **A transition goes on the part that actually changes**: putting a `BrushTransition` on `Button.Background` when the fill is set on the template's `ContentPresenter` animates a property nothing renders, with no error and no motion. And `TransformOperationsTransition`, never `TransformTransition`, for anything whose value parses as `rotate(90deg)` or `scaleY(1)`.
  - **Both viewport splitters had provably dead hover.** `Background="Transparent"` was set inline to make the nine-pixel band hit-testable, and a `LocalValue` outranks a `StyleTrigger`, so the `GridSplitter:pointerover` rule had never fired on the two controls in the window a user drags most. The transparent fill comes from the style now, and the visible ink is a separate 1px child carrying a `.hot` class written from the splitter's own enter/exit - because a child cannot read its parent's pseudo-classes from a selector, and because a nine-pixel accent band appearing under the cursor is a different control from the one that is there.
- **Avalonia style priority is a documented trap FAMILY now, and a hover audit found four more of the GridSplitter's siblings.** The rule set, in the order that decides: a LocalValue (inline attribute, code-behind assignment) beats every style; a selector with any class or pseudo-class is StyleTrigger priority and beats bare-type-selector styles; among ties, later declaration wins, which is why the shell's class styles legitimately beat Fluent's control themes and its BARE selectors legitimately lose to Fluent's state triggers. The four mechanisms that were silently eating hover: (1) **the global `TextBlock` Foreground style beats the value a label would INHERIT from its button** — every `Foreground` setter on a Button recoloured nothing, so seg labels never warmed on hover or dimmed when disabled (their icons did: a half-changed button), and the filled accent buttons showed body-grey at ~2.8:1 instead of white — the fix is a per-state `... TextBlock` rule beside every state that recolours text, never deleting the global style (Fluent's own TextBlock theme would take over, which is worse); (2) **Fluent paints many states on template PARTS at trigger priority** (`PART_LayoutRoot` for open-menu items, `PART_BorderElement` for text boxes, `NormalRectangle` for checkboxes, the scrollbar thumb's `:pressed`), so styling the CONTROL's property only reaches the part at TemplateBinding priority and loses — menu items highlighted in stock fills with the authored 90ms ramp animating a property nothing rendered, and **every focused text box grew Fluent's 2px bottom border: a real 1px layout shift on each focus**, fixed at the source by overriding `TextControlBorderThemeThickness(Focused)` and the `MenuFlyoutItem*` resource family beside the ComboBox block; (3) two fresh literal instances of the LocalValue trap (the tree's no-match counter, NameDialog's inputs); (4) missing state rules that let Fluent's win the tie (`:pressed` on the start page's rows and the ghost buttons). **The audit's healthy-list matters as much as its defects**: the class-based presenter styles (seg/tool/chip/ghost/tile/maprow/row) are all live — fix only what names the mechanism.
- **The viewport has a HEADER STRIP, and the airspace rule never blocked it.** A 28px row above the picture — chrome BESIDE the native child shrinks it rather than crossing it — carrying view-scoped state wired entirely to verbs and snapshot fields that already existed: the pipeline dropdown (whose only passive display used to live in the inspector's EMPTY state, vanishing the moment anything was selected), the grid-mode chip with its flyout of the three set-verbs, the camera toggle chip, standing amber chips for any latched F1-F5 overlay (a fat-fingered F1 used to leave a wireframe viewport with nothing on screen saying why — each chip clicks off exactly its own overlay), and a fixed-width mono camera-position readout (`FrameSnapshot.CameraPosition`, the one instrument every engine editor's status surface carries). Three changes.
  - **The engine publishes on demand.** `PublishFrame` already bypassed the interval for structural news; `EnqueueCommand` and every request latch now set the same flag, because a command the user just issued is news in exactly the same sense. What makes that safe is the rule already written down - the shell posts SET verbs, never toggles - so a stale echo can only be an older value, never the opposite of what was asked for. **The bound is the whole design**: the value a user asks for is not always the value they get (play mode refuses on a scene with no character, an edit is refused mid-gesture), so after six disagreeing snapshots the engine wins visibly, which with a transition behind it reads as a refusal rather than as a glitch. **Ticks are snapshots, not milliseconds**, because the thing being waited for is an echo and the host changes its publish rate mid-gesture. Undo and redo depth are ONE optimistic value, because they move together and predicting half of it would light the redo button against a depth that had not moved - and unpredicted it is the nastiest of the lot: click Undo, the button stays lit for 65ms, click again, two edits are gone. Scoped to the session, since a raised interrupt rate is battery on a laptop and the start page has nothing to pump; **the achieved granularity is measured and logged once**, off the UI thread, because a performance fix that silently stops working is worse than none. **`DispatcherPriority.Normal` outranks `Render` in Avalonia** (the opposite of the WPF ordering people expect), which is what puts a value the pump writes on screen in the same frame rather than the next.

- **The viewport has a GROUND now, and the depth-tested world-line lane is what made it possible.** There was no grid, no horizon, no origin and no compass anywhere: an object floating in flat sky has no scale and nothing to be positioned relative to, which is most of what "it does not feel like an engine editor" was pointing at. The blocker was that `DebugDraw` draws **depth-off, on top of the tone-map resolve** - correct for what it carries, since a gizmo handle you can see and cannot pick is worse than no handle, and completely wrong for a grid, because a grid drawn through the walls of a room is not a grid, it is a fault. So `Renderer.WorldLines` is a **second line buffer, alpha-blended over the lit scene with depth respected but never written** (`ISceneEditor.DrawWorld`, beside `Draw`). Two consequences are load-bearing. **These lines go THROUGH the tone curve and the overlay's do not**, which is right for the same reason the split exists: a grid is lit world content and should dim as exposure rises, while a handle is a display colour that must not change brightness because the camera turned - so grid colours are authored in LINEAR light, and copying a value from the overlay palette makes it arrive far too bright. And **the deferred half draws AFTER the light pass, testing depth in the SHADER**: the only depth a deferred frame owns is the G-buffer's, and rather than inventing a cross-target pass concept (a second FBO on GL, read-only DSV flags on D3D11, a two-target state on D3D12) to bind it, `WorldLineBlend.spectrashade` samples it as an ordinary texture - a render target's depth is sampleable by contract and the light pass already read it this frame - converts the texel through the same `uDepthToNdc`/`uUvToNdc` vocabulary the light pass reconstructs with, compares against its own clip z and `discard`s occluded fragments. The lane originally drew INTO the G-buffer as opaque five-attachment overwrites; see the fade bullet below for why that whole model had to go.

And no WRITE, because the lines are translucent now: a plane of one-pixel lines that wrote depth would slice whatever the pipeline submits after it, and a blended pixel has no business in the depth buffer. (`TestWriteEqual` survives in the enum; its write-the-coverage-mask rationale belonged to the retired G-buffer overwrite design and nothing draws with it today.)

Not decoration: a grid drawn at some fixed convenient size stops being the squares an object will land on the moment the user changes their snap. The `(1 - t)²` fade survives, but it moved into the shader (see the fade bullet below); GroundGrid emits WHOLE lines plus four metadata values and no longer knows how to fade anything itself. - **A light can be SEEN and CLICKED now, and it could be neither.** It carries no mesh and no brush, and `SceneNode` deliberately keeps lights out of the BVH, so a lamp was findable only by name in the tree, a marquee dragged across one *cleared* the selection, and moving one meant selecting it somewhere else and watching numbers change. **Lights stay out of the BVH** - admitting them would make every lamp collidable and query-visible, since `PhysicsFlags.Default` carries `CanCollide | CanQuery`, so a lighting change would silently alter what the player can walk into. `LightOverlay` draws a screen-constant icon per light instead and `LightPicking` ray-tests it, with **ONE shared constant sizing both**, because the symptom of two is that you click something other than what you can see. - **Lights have SHAPES now, and the uniform layout is what the whole thing turned on.** `RenderLight` carried two `vec4`s with the kind encoded as `PositionRange.w == 0` - exactly two kinds, and a third had nowhere to go. The type moved into `ColorIntensity.w` (documented as unused) and two more arrays joined it: **four parallel `vec4[8]`, never a struct array**, because a struct array generates valid-looking text and then *silently does nothing on OpenGL*, which is the worst available failure. Four is the minimum: an area light's bitangent is a cross product rather than a stored vector. The layout is `positions[xyz|range]`, `colors[rgb|TYPE]`, `axis[xyz facing | cos(outer) | halfHeight | radius]`, `tangent[xyz right | cos(inner) | halfWidth]`, and the type numbers are **append-only** - inserting one renumbers every kind after it and lights the wrong shape with no error anywhere.
  - **The refactor was done as a PURE refactor first**, with `DeferredGlTests` producing identical pixels as the proof, because every failure in this area renders a picture rather than throwing: no debug layer fires and `--offscreen-probe` passes a scene that is merely lit wrongly.
  - **Area lights use the representative point** - the spot on the shape closest to the reflection of the view ray - with ONE point for diffuse and specular, which is the honest simplification: separate points are more faithful and cost a second full BRDF evaluation per light. LTC is not reachable at all; it needs two LUT textures and a data-dependent clipping loop, which is what fxc refuses. Two lines whose absence would be a bug rather than an omission: **one-sidedness** (without it a ceiling panel lights the room above it, invisible from below and wrong everywhere else) and **range measured from the shape's closest point** (without it a four-unit panel goes dark at its own ends).
  - **Forward gets spot and not area.** A spot rendering as an omni is a lie you can see across a room; an area light rendering as a point is a highlight slightly too tight, and forward exists for MSAA and blended transparency rather than for the game view.
  - **Angles are half-angles in degrees and become cosines at UPLOAD.** The geometry is a half-angle and so is what a gizmo drags; a cosine typed into a property panel is a number nobody can picture, and converting per pixel puts a transcendental in the inner loop for a value that is constant over the frame. `OuterAngle` clamps against the inner one **on read**, because the two can be assigned in either order and enforcing it only on write would make the result depend on which came last - which is why both the map binder and `SetLightCommand.Settings` assign inner first.
  - **The pixel oracles are the schedule**: a surface inside a cone lit and one outside not, a spot aimed away lighting nothing (the `-l` sign, one character, compiles either way), a rect lighting the wall in front and not behind, and **a rect with zero extents matching a point light of the same intensity** - the cheapest possible net under the representative-point maths, and the first thing to break if the clamping, the plane intersection or the basis is wrong.
- **A surface light is a rect light flush on a picked face, parented to what owns it.** That is what "a light inside an object" means once it is built: the panel is one-sided, faces out along the surface normal, and moving the wall moves its light - which is what "inside" has to mean to be worth having. `AddNodesCommand` already carries a parent id, so it needs no new command type; the transform is built in the PARENT's space, because a world position assigned to `LocalPosition` would be offset by wherever the wall happens to be. **Sign discipline**: `Light.RotationForDirection` takes the direction light TRAVELS and a face normal points OUT of the solid, so travel is `+normal` - backwards gives a panel shining into the wall it is mounted on, silent and dark. Extents are a **fixed default and deliberately not fitted to the face**: a face polygon is derived data that changes on every carve, so auto-fitting would put a light inside the pipeline `Scene.StaticWorld` is kept pure of, and would silently resize itself the next time somebody cut a doorway through the same wall. **Stated limitation**: resizing the host brush leaves the child light where it was, because a resize rewrites planes and writes position only.
  - **`MapFormat.ToWire` was a TERNARY** (`kind == Point ? "point" : "directional"`), so every new kind would have serialised as directional - a saved map that loads as the wrong shape with nothing reporting it. It is a switch that throws now, and the reader refuses an unknown name rather than widening it. The five new members are **appended and written only when they differ from their defaults**, so a file written before they existed still round-trips byte for byte; that discipline has its own suite, because the failure is a file that is still valid and no longer identical.
  - **The reader floor moved PER DOCUMENT, not per engine.** A blanket bump would tell every older editor to refuse every map this engine writes, including the overwhelming majority carrying nothing it could not read. What genuinely needs a newer reader is a light with a shape, because `MapSceneBinder` builds a FRESH `MapLight` rather than editing the loaded one - so an older editor opening such a map and saving it would drop every angle and extent. The KIND is what is tested, not the numbers: a point light with a non-default width loses nothing that matters.
- **Ambient became a HEMISPHERE, which is the cheapest thing in the renderer that makes a scene read as being lit by a place.** It was a flat scalar, so a floor and a ceiling were lit identically and nothing in an unlit corner had any shape at all - `ROADMAP.md` calls it the single most damaging gap and it is two uniforms and one mix, against an irradiance probe's cubemap and a convolution pass. **The pair's average luminance is one, deliberately**, so the existing ambient STRENGTH keeps meaning what it meant and no scene already tuned against it is silently rescaled. Both shaders take the same pair, because the two paths share one light rig: a forward-drawn transparent surface must not sit in a differently coloured room from the deferred opaque one beside it. Landed last of the light work and the pixel oracles re-read afterwards, because it is the one change that moves every deferred pixel.
- **The light gizmo's handles are DERIVED, including which way they drag.** Each kind offers only its own (`ShapeHandles`), one function places every knob for both the pick and the draw (two would drift, and the symptom is grabbing something other than what is on screen), and the drag axis is measured as a finite difference of the knob's own projected position rather than assumed - because the handles do not share an axis: the range knob is placed along SCREEN right, a height knob along the light's own up axis, and a cone knob on the rim, so assuming screen-right makes four of the six drag sideways when pulled outward. An angle takes the ROTATE ladder and a length the MOVE one, which is the same "no fourth ladder" rule and the reason a cone snaps in the degrees the rotate tool already shows. The clamp stays in the gizmo, not the command: the angles and extents clamp in `Light`'s own setters, and only `Range`, which throws, needs guarding at the drag.

- **The world-line lane is pinned in both directions, and the investigation is worth recording because the symptom lied.** A grid drawn through the demo's walls looked exactly like a depth failure. `WorldLineGlTests` proves it is not: a line behind a mesh is occluded, a line behind a **compiled static-world brush** is occluded, in both pipelines, in a frame that runs a shadow pass. Sinking the grid to y = -60 in the running demo settled it - the walls came out clean, so the lines really were IN FRONT. **A grid plane at y = 0 legitimately slices any geometry that straddles it**, which is a wall standing on a floor whose top is at zero, and every editor in this category does the same. What was actually wrong was loudness: the fix is reach and fade, not depth. Three things that came out of chasing it and stayed: the test asserts the wall is ON SCREEN before measuring anything (the first version of the static-world case was silently measuring sky, because a compiled world with no `StaticWorldMaterial` renders nothing); the fade is `(1 - t)²` rather than `1 - t²`, because the gentler curve keeps a third of its strength exactly where the lines have converged to a few pixels apart and turn into a crawling moire; and the axes were originally clamped to a third of the grid because a hard-cut line at full strength running a hundred units across a room read as a fault — the per-pixel alpha fade later answered the same loudness properly, so they span the whole patch now and simply fade like every other line.
  - **The depth-tie half of `TestWriteEqual`'s lesson carried over into `TestNoWriteEqual`; the write-the-coverage-mask half retired with the overwrite design.** LessEqual, because a grid coplanar with a floor is exactly the case the grid exists for and GL defaults to Less - so getting it wrong makes one backend disagree with the other two about whether the grid is visible at all. The deferred half no longer touches hardware depth at all: the shader compares against the sampled G-buffer depth and discards, so sky (a cleared texel, depth 1) lets every line through with no special case.
  - **LessEqual is necessary and not sufficient**, which is why the lane has its own shader with a depth nudge. A wall's depth at a pixel is interpolated across a large quad and a line's along a line; the two land an ulp apart in whichever direction the rasteriser chooses, and half the line's pixels then fail the test - a dotted, crawling stipple rather than a grid. The nudge is toward the camera and PROPORTIONAL TO DISTANCE (a constant offset in screen depth, eight millimetres at ten units) and happens in WORLD space before the projection, so it is identical on every backend; a clip-space z offset would have to know the depth range and which way the backend's correction matrix has already turned it.
  - **The nudge is passed to the backend rather than written before the flush**, and that is the documented `Use()` trap biting again: on OpenGL `glUniform` writes into the ACTIVE program, so a value staged before `Use()` lands in whichever program was bound last. It cost one debugging round to find, silently, exactly as the note about it predicts.

- **The world-line fade is PER-PIXEL ALPHA in the shader now, because the old fade was measurably not a fade.** The first grid split every line into five flat-coloured segments, lerped each toward black by its midpoint's distance, and culled whole segments below two per cent - and over a lit floor that design runs BACKWARDS: the line colours are near-black already (0.030 linear), so `colour * k` keeps or even gains contrast against a bright surface as k falls, every segment reads at full strength until the cull snaps its 19-to-38-unit body off in one frame, and the patch re-centre jumps every patch-relative segment boundary at once. That is the "grid visibly loads and unloads in chunks" complaint, mechanism for mechanism. The only fade that works over both a bright floor and a dark one is transparency toward what is actually behind the line, so the falloff (`(1-t)²` of world distance from a centre, times a whole-lane opacity) is computed in the fragment stage from four metadata values that ride `DebugDraw` itself (`FadeCenter`/`FadeStart`/`FadeEnd`/`Opacity`, reset by `Clear`, defaults meaning "no fade") - never a wider vertex format, because the fade is a pure function of world position. Each backend uploads them at its own point in the documented `Use()` order.
  - **Blending was the one missing renderer mechanism, and it is scoped to the flush, not generalised.** D3D12 had `BlendMode.AlphaBlend` fully plumbed through its PSO key and never called with it; the line batch now takes it as a draw argument. D3D11 gets one cached blend state swapped around the flush, the exact idiom its depth states already use; GL brackets the draw with `glEnable(GL_BLEND)`. No `Renderer.SetBlendMode` was invented - the per-light-volume roadmap item can grow one when it becomes the second consumer.
  - **The fade window derives from the CONTINUOUS radius, never the step-quantised reach** - `steps = ceil(radius/cell)` makes reach jump by a whole cell as the camera climbs, and a fade window that jumped with it nudged every line's brightness on those frames. Clamped to the drawn reach only when the line cap shrank the patch, or lines would end mid-fade in a visible square edge. The axes stopped being gated on a distance test for the same reason: an axis outside the fade window renders at zero alpha, which is the same answer as not drawing it, with no edge to pop.
  - **The oracles are the two assertions the old design could not pass** (`WorldLineGlTests`, real driver, both pipelines): a 30% line leaves the wall's RED channel intact underneath (the overwrite model replaced the pixel with black albedo, so red read near zero), and one line dims along its own length under a distance fade. The occlusion pair and the coplanar-tie case carried over unchanged - the deferred half now proves the shader-side compare instead of the coverage-mask trick.
- **The grid knows when it is wanted: `GridMode` (auto / on / off), and AUTO is the default.** The grid's one job is "these are the squares this object will land on", and that question only exists while a gesture that snaps on the move grid is live - so auto shows it during translate and resize drags (select-and-move and the light gizmo's LENGTH handles included, via `LightGizmo.IsDraggingLength`; rotate deliberately not, since a position lattice beside a tool snapping in degrees reads as a 15-unit lie), and hides it otherwise. Three SET verbs on `EditorHostCommand` (`GridAuto`/`GridOn`/`GridOff`), never a cycle; exempt from `RefuseEdit` because changing what is DRAWN is not a scene edit and mid-drag is exactly when someone reaches for it; reported back as `GridModeName` on the snapshot so the View menu's radio checkmarks follow the editor. The console's `grid` verb grew the mode words beside its number (`grid 0.5` sets the increment, `grid auto|on|off` the visibility). **Visibility changes ride a fade envelope in `SceneEditorHost`** (~0.10s in, ~0.25s out, written into `Grid.Opacity` per frame): a full-viewport lattice appearing in one frame is an EVENT in peripheral vision announcing something the user already knows. **`DrawWorld` returns early while suspended**, because the engine stops calling `Update` during play but keeps calling `DrawWorld`, and a frozen envelope would otherwise leave a mid-gesture grid painted on the floor for the whole play session.
- **The editor viewport paces to the display (`Renderer.VSync`), and the demo deliberately does not.** Uncapped, the shell presented ~2,700 bitblt frames a second into a child window nobody could see the difference in: a saturated core, the GPU copying the back buffer to DWM's redirection surface at ~10 GB/s of bandwidth the compositor also needs, and every per-frame allocation multiplied by 2,700 into real gen0 pressure - and a gen0 pause stops the UI thread too, which is how an engine reading 2,746 fps makes the CHROME feel sluggish. `VSync` is a volatile flag read at `Present` time (`Present(1,0)` on both D3D backends; GL re-applies its context-state swap interval there when the value flips, the same thread-affinity trap `AcquireContext` already documents); the editor sets it, the demo stays uncapped because it is the measurement instrument and a frame time under vsync measures the monitor - `--vsync` is the opt-in, and any test asserting frame rates must leave it off. Measured in the shell: 60 fps flat, ~1% CPU, 0.1 MB/s allocated at rest.
- **The editor camera's smoothing is split per channel, because one constant cannot serve a wheel and a hand.** τ = 80 ms was tuned for the dolly, where input arrives as discrete notches and the filter turns stairs into a glide - and it was applied to EVERYTHING, so pointer-driven freelook, orbit, pan and fly all trailed the hand by ~80 ms of travel and kept drifting for 3-5τ after it stopped: the literal "transition on a drag-path value" the shell's own motion rules ban, and the single largest contributor to the editor feeling sluggish (the demo's F7 fly camera applies deltas raw, so the two could be felt side by side). `PointerSmoothingTimeConstant` (20 ms, never more than the main constant so τ = 0 still disables everything, which tests rely on) drives the look/move channels WHILE a navigation gesture is live; the dolly keeps the long constant always, and the residue after release settles on it too. **The lock also fences the pointer now**: `ClipCursor` to the viewport's client rect for the lock's duration - to the whole rect, deliberately, because a tight band around the anchor SHRINKS the travel the anchor-differencing survives a UI stall with - released inside `EndCursorLock`, which every unlock path already funnels through.
- **The 8 ms watchdog was running the FULL pump ~125 times a second, and the fix restored a documented contract as a side effect.** The timer exists for exactly one thing - the cursor-mode latch - but `OnPump` had no "anything new?" gate, so every tick re-applied the same snapshot: selection sync, the whole property panel, the snap field, four times over per publish at rest. It early-outs on reference identity with the last APPLIED snapshot now, which also makes "ticks are snapshots" true again for every `OptimisticValue` hold (they were expiring ~4x faster than designed) and for the scene panel's bounded selection wait. The other idle churn went with it: `SnapSummary` raised outside its setters' guards (two string interpolations per pump, forever), `PartialLabel`/`MultipleLabel` raised unconditionally per row per pump, and the colour row allocated a fresh `SolidColorBrush` per pump whenever a light was selected, because `Set` compares brushes by reference.

- **The pointer says what a press will do, through `ICursorShape` beside `ICursorLock`.** There were exactly two `Cursor` setters in the whole shell, and over the viewport the pointer was `IDC_ARROW` or hidden - no grab, no resize, not even mid-drag. **Shape and mode are separate seams because they answer different questions**: mode is visible/hidden/captured, shape is what the pointer MEANS, and a freelook wants Locked with no shape at all while a gizmo handle wants a visible pointer with a Grab. The vocabulary is the engine's (`CursorShape`), so **every degradation lives in the backend**: Windows has no rotate cursor and its nearest grab is the hand, Silk's standard set has neither, and a tool that had to know that would be naming a platform. **On Windows it MUST be answered inside `WM_SETCURSOR`** - the OS re-asserts the window class's cursor on every mouse move, so a `SetCursor` issued anywhere else is reverted within a frame, which is exactly the "the cursor flickers" report that has no other explanation. **The shape is DERIVED from the arbitration**, never set at each gesture's start: the camera's own gesture first (a pan and an orbit own the pointer while the viewport's drag mode is still None), then the drag mode, then the hover - so the cursor cannot get out of step with what a press would actually do, because both come from the same answer. **A selectable object gets an arrow, not a hand**: the outline is the affordance, and a hand cursor over 3D geometry reads as a hyperlink.

- **The window has a BOTTOM REGION, and its absence was one missing line.** `MainWindow`'s editor grid had `ColumnDefinitions` and no `RowDefinitions` at all, which is why nothing horizontal ever had a home and why a content browser would have become a fourth vertical column - the shape that makes a tool read as a web dashboard. Left and right now span the full height (the tree and the inspector are the two panels that genuinely want it); the centre column gains a row under the viewport, which is Godot's shape. The third `DockControl` joins the **same single `Factory`**, for the reason already recorded: a per-control factory makes a drag's target list that factory's own controls, so a panel could never cross between regions, silently.
  - **A content browser, because "nowhere for assets" was a hole in the PLAN, not only in the window.** Nothing in the shell showed a texture, a material or a model, and no milestone anywhere proposed one. It reads `ProjectLayout.AssetsPath` directly and **the shell decodes the thumbnails**, never `AssetManager`: that is the render thread's, and asking it for a preview would create a GPU texture for a picture somebody is only looking at. `Bitmap.DecodeToWidth`, not a full decode - a 4K texture decoded at full size costs 32 MB to draw at 72 pixels, and a folder of them is how an editor runs out of memory. Every navigation bumps a generation so a decode landing after the user moved on is dropped, the same shape as the asset manager's per-asset sequence ticket. **A grid of tiles here and a list everywhere else is not an inconsistency**: the rule is that a list of NAMES must be a list, and a texture is not a name - the picture IS the information and a tile is the smallest thing that can carry it.
  - **An output log, because the entire diagnostic surface of this application was one sentence anything could overwrite.** About thirty call sites wrote to it, none knew what was already there, and a failure reported while the user was looking elsewhere was gone by the time they looked back. The status line is now a VIEW of a bounded log rather than the storage. It follows the tail **only while the view is already at it**, measured BEFORE the new row is laid out - after it the extent has already grown and the test would say "not following" every time.
  - **A console that is a command line over the verbs that already exist, and says so.** There is no console subsystem: no cvars, no bindings, nothing - `docs/console.md`'s whole C-series is unbuilt, and a tab with nothing behind it is precisely the "controls that do nothing teach that this app's controls are decorative" failure. So it resolves names to `EditorHostCommand`/`GizmoCommand`/`EditorCameraCommand`/`InsertKind`/snap increments through a **hand-written table, never `Enum.Parse`** (the same AOT discipline `GizmoShortcuts.TryResolve` follows: reflection over enum names is what trimming removes, and it would fail in a published build having worked in every debug run). Every entry is a verb a button also sends, which is what keeps it from being a second path into the editor, and **`on`/`off` rather than a toggle**, for the same reason the buttons post set verbs. It shares the output log rather than keeping its own scrollback, so a command and the error it caused sit in one place in order. Numbers parse **invariantly**, because a console is typed by a person who expects a dot and a value that parses on one machine and not another is the worst kind of bug report to receive.

- **The tree stamps what a node IS, because a list of names is not a scene.** `SceneNodeKind` is derived (never stored) at the moment a change is recorded, travels on `SceneChange`, and is the only fact beyond id/name/parent that crosses the boundary. **The brush cases outrank the mesh case** (a brush node legitimately carries a renderer too) and **subtractive outranks world/part**, because a subtractive brush renders nothing at all and the tree is the only place one can be seen. **A `t:` nobody recognises matches NOTHING**, and used to match everything: the old code cleared the query so the kind test could run on it and then fell through to `Name.Contains("")`, which is true of every node in the scene, so a typo in a power feature silently reported the whole scene as a result set with nothing visibly different but a count. It resolves through an alias table of the words the toolbar and menus use (`block`, `part`, `cut`, `light`, `mesh`, `group`) rather than a substring sweep over the enum, whose own names are engine words and whose first match depended on `Enum.GetValues` order. **A zero-match filter says so in words**, because dimming is right and does mean an empty result looks exactly like a panel that broke. **Filtering DIMS rather than hides**: removing rows collapses the hierarchy around every match and destroys the user's spatial memory of the scene on the first keystroke, so the filter walks the flat index setting a flag and rebuilds no collection at all. Ancestors of a match are promoted to context so a hit three levels down is reachable, and the parent map that needs is built in ONE pass rather than searched per match.
- **The scene tree is a FLAT list, and that is what makes it virtualize.** Avalonia's `TreeView` never overrides its items panel, so it inherits a plain `StackPanel` and realises a container per node whether or not one can be seen: at the engine's own documented ceiling of 25,000 nodes that is twenty-five thousand rows built to show thirty-five. `SceneTreeModel.Rows` projects the hierarchy to only the currently visible nodes, each carrying its own `Depth` (a flat list has no nesting left to indent by) and `HasChildren`, and a `ListBox` over it virtualizes by default. **Measured on the demo: 34 rows realised of 245 visible, 257 in the scene.** **The projection is PATCHED, never replaced**: assigning a fresh collection resets scroll and selection, so expanding one group would throw the user back to the top of the scene; the recompute produces a desired list and inserts and removes the difference, which for expand, collapse and add is one contiguous run. **Expansion goes through the model** (`ToggleExpanded`), because it is the INPUT to the projection and a chevron writing the flag directly would leave `Rows` describing a tree nobody has any more. **Two things the framework does that had to be worked around**: `ListBox` swallows Left and Right (on a vertical panel its selection move re-selects the current row, returns true and marks the event handled), so the collapse/expand keys are a TUNNEL handler rather than the bubbling one XAML attaches; and Fluent hangs the row fill on the template's presenter per state, so a single transparent setter is beaten the moment a row is selected and the system accent comes through as a bar the theme never chose. **`Avalonia.Controls.TreeDataGrid` is the obvious alternative and it is not free**: 12.x is a commercial Avalonia Pro component whose build fails outright without a licence key, and the last permissively licensed release predates Avalonia 12.
- **Picking in the viewport scrolls the tree to the node, and the expansion has to be MODEL state for that to be possible at all.** A row under a collapsed parent has no container to scroll to, so `IsExpanded` lives on `SceneTreeNode` (bound two-way) rather than on the container, and `TryReveal` walks the maintained parent map opening the chain above the node. It **only ever expands**: the expansion set is the user's, and a reveal that tidied up on its way past would undo their work on every click. It does **not** expand the node itself, because picking a group means "show me this", not "show me its two hundred children". **Three gates keep it from being annoying**: only on a CHANGED selection, only when the change did not come from the tree itself (a row the user just clicked is already on screen), and never while the filter box has focus, which is the single most-complained-about behaviour in editors that ship this. **The resting position is set by writing the scroll offset directly**, a third of the way down the panel: minimal scrolling parks the row against an edge where it has neighbours on one side only, and the tidy-looking alternative of asking for an oversized `BringIntoView` rect does nothing at all, because the rect is clamped to the control (measured: the row landed on the top edge one time and the bottom the next). **The scroll runs one dispatcher hop after the selection**, since selecting starts the framework's own scroll and measuring before that lands reads a pre-scroll position and overshoots.
- **`SceneTreeNode` raises change notification, and the delta-set selection is what makes that affordable.** Without notification a binding reads each property once, so the two paths that rewrite a node in place - a reparent, and a re-add under the same id when a delete is undone - left the tree showing a name the node no longer had, with nothing reporting it because the structure was correct. Adding notification then made the naive selection pass dangerous: it cleared every flag and re-set the selected ones on every published snapshot, which against the engine's own 25,000-node ceiling is a notification storm proportional to the whole scene rather than to what changed. `ApplySelectionCore` now diffs two id sets and swaps them.
- **A shell must DRAIN snapshots, never sample the newest one, and this is the trap the whole host contract hangs on.** `EngineHost` guarantees every structural change rides the NEXT snapshot out, which makes each snapshot's change list a batch that exists exactly once. The first one carries the "you have nothing, rebuild" flag, so keeping only the latest lost precisely that one and left the editor's tree view showing **4 nodes of a 257-node scene** with nothing anywhere reporting a problem: the engine kept its promise and the shell broke it from the outside. The shell now queues every published snapshot, bounded the way `SceneChangeLog` is and reporting overflow the same way, and applies each exactly once; **selection is applied from the newest one only**, because it is a state rather than a history and the walk is over every node in the tree. The mirror rule on the other side is that an overflow is answered by asking the render thread for the whole graph through `EnqueueCommand`, which comes back as a pre-order list of `Added` changes in the same shape the log emits, so there is one apply path rather than two.

- **Engine-level state a UI drives goes through request latches on `EngineHost`, in the exact shape of the title and cursor latches.** Play mode, the debug visualisations and the pipeline are ENGINE state, not scene state, so `EnqueueCommand`'s `Action<Scene>` cannot reach them and handing a shell the `Engine` would hand it every render-thread-only member. Each is a thread-safe latch (`RequestPlayMode`, `RequestDebugVisualization`, `RequestPipeline`) the render loop takes at the same site the matching key press is read, so a button and a key cannot disagree; latches rather than a queue because every one is last-write-wins state, and a queue would replay a stale intermediate click. **Set semantics, never toggle verbs, for anything a control displays**: a toggle sent against a snapshot one publish stale flips the wrong way exactly when the user clicks fastest, which is also why `GizmoCommand` grew idempotent `Use*/Enable*/Disable*` halves beside its keyboard toggles, and why `FrameSnapshot` now reports the state back (`IsPlaying`, `CanPlay`, `DebugFlags`, `PipelineName`/`PipelineNames`, per-tool snap increments). Ctrl chords whose letter is also a camera movement key stand down while a camera claims the letters (Ctrl is descend, so Ctrl+A is descend-plus-strafe-left, not select-all), in the editor's keymap AND in the viewport's shell-chord interception while the cursor is locked.
- **The shell is project-first: it opens on a start page, and a session exists per project.** No engine runs until something opens - the start page (recents, new project, open project, loose bundle) is ordinary Avalonia with no airspace constraint, and "no session" and "no viewport control" are the same state on purpose: the viewport is created in code when a launch begins and removed when the session closes, because a `NativeControlHost`'s child window lives exactly as long as the control is in the tree. **The asset content root is a constructor argument of the session**, fixed at birth to the project's `Assets/`, so opening a different project is a new session the way it is a new window in every IDE. A session boots the `Baseplate` startup scene (a sun and a ground plate - also what "New map" produces, so "new" means one thing) and the real map then opens through the ordinary map path where failures carry a report. **Saving a map inside the project writes the manifest back by RE-READING it from disk first** - the manifest is the author's file, and writing the copy loaded at open time would silently revert every hand edit made since; re-reading is also what makes a retry after a failed write work. **Document callbacks carry a session-boundary guard**: an OpenMap/SaveMap completion posted from a torn-down session's render thread must not rebind the fresh session's document, or the next Ctrl+S overwrites a different project's bundle. Recents persist per user through a hand-rolled AOT-safe codec that merges with what another shell wrote instead of clobbering it. The window close button gets the same typed discard confirmation every menu route has.
- **The command surface is FIVE MENUS and ONE row of clusters, and the tab strip that used to be here was retired on evidence.** The strip was Home / Model / View, and it was killed by three things: Home and Model carried the same six verbs, Frame was written out three times, and the one thing a first session actually needs - inserting an object - lived on the tab nobody opened. Switching mostly did nothing, which teaches within a session that the tabs are decorative. Two changes made one row enough. **The structural verbs left the bar entirely** (duplicate, group, ungroup, delete): they were four anonymous outline glyphs, and they are already on the keyboard, in the Object menu and in every row's context menu, so the toolbar copy was pure redundancy at four glyphs' cost. And **the debug overlays and the pipeline became menu items**, which is affordable now that the airspace rule is known to spare popups. What is left is Move/Rotate/Size, snap, the two mode chips, undo/redo and Insert - and Insert is on the row, first among equals, because it is the group that answers "how do I put something in the world".
  - **Five menus, because a popup is a real OS window.** File, Edit, Object, View, Help - each verb printed with its shortcut beside it, which is the cheapest discoverability the shell can buy and the second of the three routes every command owes (direct manipulation, a menu with the shortcut, and eventually a palette). `InputGesture` is **parsed by Avalonia, not merely displayed**: `"["`, `"Del"` and `"2"` throw `ArgumentException` out of `KeyGesture.Parse` at window construction and take the whole app down at startup, so gestures are written as real `Key` names (`OemOpenBrackets`, `Delete`, `Ctrl+D1` - which renders as "Ctrl+1", because `KeyGesture.ToString` maps the digit keys back).
  - **ONE snap field, tied to the live tool.** It was three, labelled `mv`, `rot` and `sz`, which asked the reader to hold a mapping from abbreviation to tool in their head for a tool they had already chosen. The box holds the live tool's increment, the unit beside it says which unit that is (`su` / `deg`), and `ShellModel.GizmoModeChanged` is what re-reads it when the tool changes - without that the box keeps the previous tool's number beside the new tool's unit, which is a worse lie than showing nothing. Backed by `SetSnapIncrement(tool, value)`, the payload-carrying sibling of the snap verbs.
  - **Play sits in the menu row's far corner**, always visible and never one of a crowd, because stopping a run must never be two clicks away; its glyph is success-green (the brand red means selected here, and a red play button reads as record) and it carries its word, since it is the one control with room for one. **A window chord on a PRINTABLE key must stand down while a text box has focus.** Avalonia's `TextBox` marks `KeyDown` handled only for caret and editing keys, so an ordinary letter bubbles to the window and its `KeyBinding` runs: a bare F for "frame the selection" fired on the F of "Floor" typed into a rename box, blurring the box (which commits the half-typed name) and framing. The guard is on the KEY rather than on the binding, because a function key carries no such risk and F8 must keep working from anywhere. **Document chords are window key bindings AS WELL as viewport interceptions** (two routes, one handler each - the viewport route exists because the OS gives a focused native child the keyboard and Avalonia never sees it), and a chord blurs-and-commits any focused field before acting, or Ctrl+S saves without the value just typed while reporting success. **Focus is handed to the engine with Win32 `SetFocus` on its HWND, never Avalonia `Focus()`** - a `NativeControlHost` is not focusable and the call is a silent no-op, which left Escape stranding the caret in a field where the next tool key typed into it.
- **The editor inserts things (`SceneEditorHost.Insert`, `InsertKind`), and the placement rules are the feature.** One history entry, selected afterwards, placed on the surface at the CENTRE of the view by the same scene-wide raycast picking uses - parts and meshes included, because a ray through the compiled world alone passes straight through a parts-built platform and buries the insert underneath what the user was looking at. An additive brush rests flush (pushed out by its half extent along the hit normal); **a hole starts HALF-BURIED, because a resting negative carves nothing by design** (coplanar opposite-facing coincidence is a no-op in the carve), so flush placement would produce a magenta outline sitting on intact geometry forever. The grid snap aligns the position ALONG the hit surface only - snapped, then re-projected onto the hit plane, with the clearance applied after - so a coarse grid can neither bury an insert nor float it. A subtractive insert is always world-kind (a subtractive part is the pairing that cancels to nothing), and inserting cancels a live marquee first, exactly as a selection change does.

- **The scene tree is an OUTLINER, not a list of names, and every gesture it grew is a verb the engine already had.** Multi-select (Ctrl/Shift), Delete/F2/F and the Ctrl chords with the tree focused, in-place rename, drag-and-drop reparent with before/into/after drop zones, and a context menu on every row - each one resolves to `SelectByIds`/`RenameById`/`ReparentByIds`/`Apply(EditorHostCommand)` on the render thread, addressed by id, so there is still exactly one path from a gesture to an edit. **A rename now rides the change log** (`SceneChangeKind.Renamed`, raised by the `SceneNode.Name` setter through `Scene.NodeRenamed`): a rename is neither a membership change nor a reparent, so before it existed the mirror kept showing the old name until an unrelated structural change happened to rewrite the row. Three shell-side guards are the difference between this working and quietly destroying data. **`SceneTreeModel.IsPatchingRows` is checked before any selection is posted**, because a list control drops removed items from its selection and reports that exactly as it reports a click - so collapsing a group told the engine "the user deselected everything inside it", and the selection was gone for good (every path that folds rows away funnels through `SyncRows`, which is why one flag covers the chevron, the Left key, collapse-all, an engine-side delete draining in, a filter re-run and a whole-graph rebuild). **An additive gesture unions the engine-selected rows that are hidden** under a collapsed parent, since the list can only report what it can see. And **the panel holds the selection it just asked for until the engine echoes it**, because every snapshot published in between still describes the selection the gesture replaced; writing that back would undo the click and make the next Ctrl-click compute against it. The wait is bounded and then defers to the engine, which is authoritative - an echo that never matches (an id that left the scene) must not freeze the panel's view of the selection forever.
- **A multi-node reparent is applied in TWO PASSES, and that is not an optimisation.** `ReparentNodesCommand` carries each node's index in the ALL-MOVERS-VACATED model - where it sits in the finished list - so applying the moves one at a time is wrong the moment two nodes move within one parent: when the first is inserted the others still occupy their old slots and it lands beside them instead of where the drop pointed. Undo had the mirror defect, which is worse, because it made undo **not an inverse**: dragging two siblings and pressing Ctrl+Z left them permanently swapped, and no further undo or redo recovered the authored order. Parking every mover at the end of its destination parent first makes the vacated model literally true (the prefix of each list is then exactly its non-movers, and an insert at any index up to that prefix cannot be disturbed by the movers parked behind it), so the second pass places them correctly in both directions. Cross-parent moves were always correct - the destination never held the movers - which is exactly why group and ungroup passed throughout and no test caught this. Two smaller rules ride along: the destination shift is counted against the ORIGINAL target rather than a running total (comparing each root to a progressively decremented index makes the answer depend on which row was Ctrl-clicked first), and the dragged block is sorted into the TREE's order rather than the click order, because sibling order is placement order is authored data. A drop that asks for the arrangement the scene already has records nothing, the same refusal a rename makes for an unchanged name.
- **`OnSceneReplaced` must NOT latch the suspension, and getting that wrong made the whole editor inert.** It called `Suspend()`, which does two useful things (roll back an open gesture, release the camera's cursor lock) and then sets `IsSuspended` - a flag only the play-mode exit ever clears. So opening a map left the editor permanently refusing every mutating verb: insert, delete, duplicate, group, rename and every property edit answered "refused, play mode owns the scene" at Debug level and did nothing, in an editor nobody was playing. Whether it bit was a RACE between the queued map-open command and the editor factory - an editor that did not exist yet took the null-conditional and survived - so the shell worked on some launches and was inert on others, which is the hardest kind of fault to report and the reason it stood. The lifecycle hook now does the rollback directly and writes the flag in neither direction, which also preserves a suspension that is real: a scene replaced while play mode owns it stays suspended.
- **A hand-written `private void InitializeComponent() => AvaloniaXamlLoader.Load(this);` SHADOWS the generated one, and every `x:Name` field then stays null.** Avalonia's name generator emits `InitializeComponent(bool loadXaml = true, ...)` plus the field assignments; a parameterless declaration in the same partial class wins overload resolution at the `InitializeComponent()` call site, so the XAML loads and nothing is wired. `NameDialog` did this and threw a `NullReferenceException` on its first line for its whole life - which is every "new project", "new level" and "save as" in the shell, each one surfacing as a crash or, where the caller was a fire-and-forget `Task`, as a dialog that silently never appeared. The rule is simply not to write one: the classes that do not (the window, the panels) have always worked.
- **The editor knows when it is suspended, because a UI's view of play mode is stale by construction.** A shell gates its own surfaces on a published snapshot up to a publish interval old, so a click landing in that window enqueues an edit that arrives at a suspended editor and lands in a scene somebody is walking around in; a context menu already open when play starts can keep sending them indefinitely. `ISceneEditor.Suspend`/`Resume` are therefore a pair (the engine calls `Resume` when play mode exits), `SceneEditorHost.IsSuspended` is the authoritative answer, and every mutating verb goes through one `RefuseEdit` gate that also carries the mid-drag refusal the structural verbs already had - which is what stopped a rename committed by the blur that a gizmo grab itself causes from opening a transaction inside the drag's own, throwing, and being logged at `ERR` while the typed name was dropped. Navigation and clear-selection stay live while suspended: neither is a scene edit.
- **A right-click in the viewport is a press that never became a drag, measured as DISPLACEMENT.** The engine's freelook owns a right drag, so the shell can only claim the click - and Windows itself defines that as a rectangle around the press point the pointer has to LEAVE (`SM_CXDRAG`, per-window DPI), with no time component. Summing the path length instead made an ordinary hesitant click on a high-dpi mouse silently open no menu while pressing faster "fixed" it, which is the signature of a bug nobody can report. The travel accumulates through both move shapes because the cursor lock engages within a frame or two of the press and everything after it arrives as a delta. **The retarget uses the PICK's reach, never the insert clamp**: they answer different questions, and reusing the insert's 200 units meant a right-click on anything further away silently kept the previous selection - indistinguishable from the empty-space rule, and enough to put the menu's Delete on an object off screen.
- **A structural edit restores the PLACEMENT, not merely the node, and the sibling index is the load-bearing half of that.** Child-list order is traversal order is the static world's placement-slot order, and placement order breaks ties in the carve's overlap ordering, so a node that comes back from an undo at a different index rebuilds a level that is valid, different, and **bit-unequal** to the one that was there. `SceneNode.InsertChild(index, child)` exists for exactly that (`AddChild` is now its append case), and `AddNodesCommand`/`RemoveNodesCommand`/`ReparentNodesCommand` record parent id plus index. **No pre-existing oracle covered this chain**: every determinism and chunked-vs-monolithic test builds a literal `BrushPlacement[]` and calls `CsgWorld.Build`, which is blind to the step that decides what the placements are, so an `InsertChild` that silently appended would have left the whole suite green (`StructuralOrderTests` is the test that closes it). **A node carries THREE payloads and a clone treats each differently**: `MeshRenderer` shared by reference (immutable, renderer-owned), `Brush` cloned via `CloneShape()` not for mutability but because `CsgCompileCache` keys on reference identity and one shared instance makes every duplicate past the first re-carve on every compile forever, and **`Light` copied because it is the one MUTABLE payload** (sharing it makes dimming the copy dim the original). `PhysicsFlags.HasBody` is stripped from a clone: it is physics-owned and names a side-table entry belonging to the original. The four verbs live in `StructuralEditor` as compositions of those three commands rather than as four more command types, they operate on the selection's ROOTS (a node an also-selected ancestor already carries must not be recorded separately, or its undo names a parent that is still deleted), and each lands as exactly one history entry. Two bugs this uncovered and fixed: `Scene.OnNodeAdded` never rechecked light membership while `OnNodeRemoved` dropped it unconditionally, so a deleted-and-undone light was extinguished silently and permanently; and `AddChild` had no cycle guard, which a reparent reaches by ordinary slip and which surfaces as a hang on the next frame that walks the graph rather than as an exception.
- **The character is engine furniture, and it walks on PLANE SETS rather than hulls.** `CharacterMover` is a static tick over a `CharacterState` struct — sweep-and-slide, step probe, ground snap, slope limit, Quake-shaped accelerate/friction — driven through `ICharacterCollisionSource`, whose brush-plane implementation is what makes a doorway walkable at all: the compiled solid is `⋃additive \ ⋃subtractive`, and `A \ N` is exactly the union of `A ∩ {hₖ ≥ 0}` over N's planes, so an *overlapping cover* of convex plane lists represents the bite a negative takes out of a brush, which one convex hull per brush fundamentally cannot. `FirstPersonController` lives in Core beside `FlyCameraController` and for the same reason (a shipped game needs a character; it does not need gizmos), so the engine drives it directly rather than through a seam. **The frame/tick split is load-bearing:** input is sampled once per frame into ONE `CharacterCommand` that every tick of that frame replays, which is only safe because the command carries absolute yaw/pitch rather than mouse deltas and the mover derives the jump edge from its own previous buttons — sampling per tick would multiply look speed by the frame's tick count. The eye is placed from the tick pair blended by the accumulator's `Alpha`, the same trade `PublishRenderPoses` already makes for every other body — one tick of view latency for a view that moves at the frame rate rather than at 60 Hz. Entering play mode is a transfer of two exclusive resources: the engine calls `ISceneEditor.Suspend()` (roll back any open gesture, release the editor camera's cursor lock) *before* the character asks for the cursor, and while it is active neither the editor nor the fly camera runs. **The collision source's world lane is a REGION invalidated by CONTENT, not by the compile counter**: a scene where anything animates recompiles hundreds of times a second (the demo's bobbing pillar alone), so comparing the region's selection — brushes by reference, transforms by value — turns 1,498 rebuilds per 25 seconds into 1. Contact planes are deduplicated by normal *and* separation for the same reason overlapping brushes are normal in a CSG world: a staircase is boxes sunk into the floor and a ramp is a wedge buried in it, so one physical surface would otherwise spend the whole 8-plane contact budget on copies of itself and drop a wall.
- **The host wires the editor in; the engine only knows a seam.** Core cannot reference `SpectraEngine.Editing` — the dependency runs the other way, which is exactly what keeps gizmo/undo/tool code out of a shipped AOT game binary — so the engine loop drives the editor through `ISceneEditor` (one `Update` per frame, one `Draw`, and the counters the periodic stats line reports) and the executable supplies the implementation through `SceneManager.EditorFactory`, invoked on the render thread once the scene is built. A host that sets nothing gets a demo that animates and renders but does not select, which is what a game wants. `DemoEditorHost` is the only type in the process that names both `Silk.NET.Input.Key` and the editing assembly: it resolves physical keys into `GizmoCommand`/`EditorCameraCommand` verbs **once, at construction** (the shortcut tables match on key *names*, so resolving per frame would allocate a string per key per frame) and returns from `Update` whether it drove the camera — which is the whole of the navigation toggle. **F7 flips between the editor's freelook camera (the default) and the engine's original fly camera**; picking, manipulation and box select run in both, and `ISceneEditor.NavigationModeName` puts the live one in the periodic stats line so a smoke run can tell which is driving. The host feeds the movement axis to the editor camera *only while the look button is held*, which is both what the gesture means and what leaves `W`/`E` free to mean "switch tool" the rest of the time; the fly camera reads the keyboard itself, so while it drives the conflicting letter-row tool keys stand down as before. **Gizmos and the marquee draw through the same depth-off `DebugDraw` line pass as the selection highlight**, on all three backends: handles are drawn on top of the geometry they manipulate, which is the only way what you can see stays what you can pick.
- **The demo can prove the whole editing chain to itself every five seconds, with no human and no mouse — but only when asked.** The self-test is **opt-in and OFF by default** (`--selftest`, `SPECTRA_SELFTEST`, parsed by `DemoStartupOptions`; the host simply passes a null subject node when it is off, and `DemoEditorHost` then builds no test at all). It is gate instrumentation, not demo behaviour: the drag is a *real* one-world-unit move of a *real* brush node that stays displaced for the frames the async recompile needs, so leaving it on means the scene visibly pops every five seconds with nobody touching the mouse — which is indistinguishable, from the outside, from a brush-only jitter bug, and was once reported as exactly that. When it IS on, startup says so in one line. `EditingSelfTest` screen-ray picks a known brush node (`SceneManager.SelfTestNode` — deliberately one whose chunk cells nothing else in the demo dirties, so the recompile evidence is attributable), grabs its x translate handle, drags over several synthesized `EditorInputFrame`s to a known world delta, commits, and asserts that the node moved by exactly that delta, that the grabbed manipulator emitted line geometry, and that the compile launched afterwards dirtied that node's cell — then undoes and asserts the transform came back **bit-for-bit** (absolute-value commands make exact equality the right assertion, not a tolerance), redoes, and undoes again so the scene is left precisely as found and the run can repeat forever without drifting. One PASS/FAIL line per run carrying the measured delta; failures log at `Error`. Three details are load-bearing. It runs on a **private** `UndoStack`/`GizmoController` rig, never the live one, so it cannot pollute the user's history or fight a gesture in progress. It **borrows and returns** the scene camera (parked at a fixed offset from the node, so the answer does not depend on where the user has navigated) and the selection inside a single frame, so nothing is ever drawn from them. And the undo **must wait for the compile carrying the move to land** — the scene's dirty diff compares placements between snapshots, so a move undone before the next snapshot dirties nothing at all, and a self-test that undid immediately would assert on an empty dirty set.
- **Demo animation is the frame's last writer, so it must yield to edits.** The engine runs the editor first (`ISceneEditor.Update`) and `SceneManager.Update` after it, so anything that recomputed a pose from a rest position captured at load would silently discard every gizmo drag, undo and redo aimed at that node *within the same frame* — a tool that looks broken rather than a demo that looks busy. `DemoBobAnimation` (the bobbing `PillarA`) therefore re-centres on whatever it finds on the node when it did not write it itself, cancelling out its own last offset so the hand-off does not snap the node by an amplitude. Any future demo animation on an editable node owes the same courtesy.
- **The scene is tone-mapped on its way to the window, and that is where linear light stops.** The frame renders into a half-float target (`Rgba16Float`, linear) and one full-screen pass applies exposure, an ACES curve, and the hardware sRGB encode the back-buffer format already performs. **There is no `pow` in the resolve shader**: the encode belongs to the target's format exactly as the decode belongs to the sampler, and doing it in the shader as well is a double encode that washes the picture out. An 8-bit intermediate would be worse than none, because linear 8-bit spends its codes on highlights nobody can distinguish and bands the shadows. **The V coordinate is flipped on D3D only**, baked into the full-screen triangle's vertex data: GL framebuffers have a bottom-left origin and D3D render targets a top-left one, so an identical mapping renders one of them upside down, and uploaded textures never reveal it because `ImageDecoder` flips image rows on the way in while a rasterised target does not pass through that code. This produces no error of any kind on either backend, so it is asserted with a pixel (`PostResolveGlTests`) rather than reasoned about. The triangle carries a **real vertex buffer and the full standard layout** because SpectraShade has no vertex-ID input and D3D11 builds every input layout from the lit shader's bytecode. **`DrawFullscreen` is per-backend** because there is no shared order: OpenGL needs `Use()` before the uniform writes and both D3D backends need it after, and `Use(); set; Use();` is worse still since D3D12's first `Use()` clears the pending texture table and the pass then samples the white fallback. **Debug overlays draw in their own pass on top of the resolve**, never inside the scene's: gizmo handles and the selection highlight are authored as display colours, and tone-mapping them would make a handle's brightness depend on what the camera was looking at.
- **Lighting is deferred, and the split is what makes lights cheap.** The `Deferred` pipeline (one per backend, beside `Forward` and `Wireframe`; `--pipeline=<name>` or the rotation key selects it) rasterises surface properties into a five-attachment G-buffer once and then shades the whole screen in a second full-screen pass, so the bill stops being draws times lights. The layout is a contract written down on `GBuffer` and read by two shaders that can drift: albedo+AO, normal+roughness, metallic+shading-model, emissive, and a per-shading-model `custom` channel. **Position is not stored**, it is reconstructed from depth, which saves a whole RGBA16F for something already written. The BRDF is Cook-Torrance: GGX, height-correlated Smith (the two sqrts are the point, and Schlick's `k` approximation is what rings a smooth silhouette with a bright rim), Schlick Fresnel, and F0 lerped from 4% dielectric to the albedo by metallic. **The geometry pass overrides the material's shader and keeps its parameters** (`Material.ApplyTo`), so every `.spectramat` written before deferred existed renders in both paths with no migration, and `AssetManager` seeds the full PBR surface set on every material because one program draws every surface and an omitted parameter inherits the previous draw's value rather than a default. Three details are load-bearing. **The colour attachments are never cleared**: the depth buffer IS the coverage mask, the light pass returns the sky wherever depth is still 1, and clearing anyway is five full-screen writes nothing reads (on D3D12 it is also slower, because a clear to a value the resource was not created with takes the unoptimised path and says so per attachment per frame). **The G-buffer is sized to the window, never to `FrameTarget`**: a frame can run its pipeline more than once into differently sized targets (the offscreen probe does), and following the target resizes the G-buffer mid-command-list, which on D3D12 releases a resource the open list references. And **the depth texel is converted to NDC z by a per-backend scale and bias** (`Renderer.DepthToNdcZ`, the mirror of `ClipZCorrection`), because a depth buffer stores 0..1 everywhere while clip z does not; get it wrong and every position reconstructs on the right ray at the wrong distance, which throws nothing, logs nothing and simply lights the scene incorrectly, so it is pinned with a pixel (`DeferredGlTests`). **The light pass snaps every G-buffer read to a texel centre and derives its clip-space xy from THAT point rather than from the interpolated one**, because the G-buffer's size and the pass's size are independent: when they differ, several pixels land on one depth texel, each carrying its own interpolated ndc, and reconstructing with that against a depth measured elsewhere puts the position on *this* pixel's ray at *that* pixel's distance. The point slides along the surface — invisible head-on, several times the real error at grazing angles — and it made a lone sphere self-shadow by 369 of 765 at a 96 probe against a 64 G-buffer where a matched pair read 45. The snap is exactly a no-op when the sizes match (uv is already `(i+0.5)/size`), so the window path cannot be disturbed by it, and `uUvToNdc` is *sent* rather than assumed because `FullscreenTriangle` bakes a V flip into its vertices on D3D and guessing that sign renders one backend upside down silently. **`--offscreen-probe` renders at 640x360 against a 1280x720 window, so it hit this every run and could not see it**: it reads debug-layer error counts, and a wrong picture raises none. **Forward stays in the rotation** for the cases deferred structurally cannot do: hardware MSAA (averaging two normals or two material ids is meaningless) and blended transparency (one surface per pixel, by construction).
- **Shadows are four directional cascades in one depth atlas, and the parts that keep them still are not polish.** The frame's first DIRECTIONAL light casts; point lights need a cube map, which `Renderer.CreateTexture` has no path for. `ShadowMap` fits an ortho box to each of four SLICES of the camera frustum out to `Distance` (60 units), because the world is unbounded and there is nothing else to fit to, and everything past it is lit but never shadowed. **Cascades are what makes the near shadow sharp at all, not a quality setting**: one box over the whole range puts a texel 3.6 cm across right where you are looking, the 3x3 filter kernel spans three of those, and a 40 cm post gets a penumbra a third of its own width and reads as a smudge. Four boxes put the near texel at 5.7 mm and the penumbra at 3 screen pixels instead of 22 (measured, not estimated). **The slice is bounded by a SPHERE and the box is then snapped to whole texels**, and the two only work together: the sphere makes the texel size independent of where the camera looks, and the snap then has a fixed grid to quantise to. **Light space is anchored at the WORLD ORIGIN, not at the slice**: putting the light's eye at the slice centre is the obvious choice and it silently destroys the snap, because the frame itself then slides with the camera and quantising inside a sliding frame quantises nothing (`ShadowMapTests` measures a fixed world point stepping in whole texels, and fails on both mistakes). **The four cascades share ONE depth texture as a 2x2 atlas** and one sampler, because SpectraShade cannot pass a sampler to a function and four textures would mean the filter kernel written out four times; `Renderer.SetPassViewport` narrows the pass to a quadrant, and its y origin is the v = 0 edge on every backend because GL's bottom-left viewport and bottom-left texture row cancel exactly as D3D's two top-left conventions do. PCF taps are clamped inside the cascade BEFORE the atlas offset or they read a neighbouring cascade's projection. **Casters are culled per cascade against the LIGHT** through `Scene.BuildShadowView`, never reused from the camera's list, or a wall just off screen would stop shading the floor the moment you turned. The pass is **depth-only** (`RenderTargetDesc.DepthOnly`, no colour attachment, no render target bound) with a **void fragment stage**, which SpectraShade allows now because a pixel shader that returns a colour with no RTV bound makes D3D11 log a warning PER DRAW into the same info queue the engine reads to detect real errors. Bias is a **normal offset in texels of the CHOSEN cascade**, so the near cascade gets a small offset and the far one a large one for free; one global value is either useless far or eats every near shadow whole. **The slope-scaled raster bias is coupled to `FilterRadius` and must cover the filter's whole FOOTPRINT rather than one texel** — a tap compares the receiver against a texel up to the radius away plus the one the bilinear weighting straddles, and on a surface grazing to the light the stored depth there belongs to a visibly different part of the surface. It shipped at 2.5, tuned for a point sample and never revisited when the filter was widened, which left a lone sphere falsely self-shadowing along its terminator by 102 of 765 (the mottling reported on the demo's PBR spheres). Swept as the smallest slope term leaving zero acne: radius 0/0.4/0.8 need 6, 1.2 (the default) needs 8, 2 needs 10, 3 needs 14 — so **widening the filter without raising the bias brings it straight back**, and the cost of the correction is about 1.6% of cast-shadow area. Two things this ruled out by measurement, both textbook: **receiver-plane depth bias made it worse** at every useful clamp (102 disabled, then 120/171/219 as the clamp rose; the opposite sign was uniformly worse, so the derivation was right) because at 512 one screen pixel spans ~0.46 shadow texels while the taps sit 1.2 out, so a plane fitted over that baseline does not survive extrapolation across a curving grazing surface — taken from the exact facet plane the same correction is perfect, so the estimator is what fails; and a **constant `CompareBias` ×16 also reaches zero** but is a margin rather than a fix and does not scale with slope. Every backend convention (the Y flip, clip Z to depth buffer) is folded into `ShadowMap.WorldToShadow` on the CPU so the shader carries none.
- **Measure the frame before optimising it, because two of the three biggest costs were not where anyone would look.** `--profile` turns on `FrameProfiler` and the periodic stats line then reports where the frame went, phase by phase, plus mesh and compile churn. What it found: **OpenGL was pinned at exactly 16.68 ms with 0.8 ms of work in it**, because `glfwSwapInterval` acts on the context current on the CALLING thread and the engine hands the context to a dedicated render thread straight after creating it, so the main thread's `VSync = false` applied to no context at all. `OpenGLRenderer.AcquireContext` sets it again over there: 16.68 ms to 0.74 ms, and no shader or draw call was involved. And **D3D12 spent 7.2 ms of a 10 ms frame inside `CreateCommittedResource`**, at roughly 480 microseconds a mesh against D3D11's 24, because a moving world brush makes the static-world compiler land fresh chunk meshes every frame. `D3D12Renderer`'s mesh buffer pool hands freed buffers back out instead, bucketed to powers of two so a chunk that gained a few triangles still hits the same bucket, and retired through the existing fence wait so a buffer is never reused while the GPU still reads it: 7.2 ms to 0.10 ms. **Neither was in the renderer's drawing code**, which is exactly why the frame time was identical at 1280x720 and 2560x1440 and why guessing would have optimised the wrong thing.
- **The graphics validation layer was on in every build, and it was the single largest cost in the frame.** Both D3D backends asked for it unconditionally and only fell back when the machine had no Graphics Tools, so every measurement anyone ever took on a developer machine included validation and a shipped build would have carried it. D3D12's layer validates every command-list call. Turning it off is worth **2.3x on D3D11 and 2.7x on D3D12** in the demo, which is more than every other optimisation in this session combined. `Renderer.EnableDebugLayer` now defaults to on in Debug and off in Release, with `--debug-layer=` to force either. **The catch is that the engine's own error gate reads `DebugLayerErrorCount`, which on D3D exists only while validation runs**, so `--offscreen-probe` warns loudly and downgrades its own verdict wording when the layer is off: half of what that probe claims to prove is that the layer stayed silent, and a silent layer that is not running proves nothing. A gate that quietly weakens is worse than one that fails.
- **The low-power test rig is the machine you already have.** `--adapter=<substring>` picks the D3D adapter by name, so a desktop with a discrete card and an integrated one can measure both, and "how does this run on weak hardware" stops being a guess. `--size=WxH` sweeps resolution, which is what separates the two halves of a frame: on the integrated part the demo fits **0.36 ms of CPU plus 2.9 ms per megapixel of GPU** almost exactly, and on the discrete one the slope is unmeasurable because the frame never stops being CPU-bound. **What that per-pixel number is made of is the important part**: at 1080p, forward costs 2.4 ms and deferred costs 6.4 ms, so the G-buffer and its light pass are worth more than the entire rest of the frame on integrated graphics. 36 bytes per pixel written and read back is roughly 160 MB of traffic a frame, which is DDR bandwidth the CPU is also using. **One of those five attachments (custom) is written every frame and read by nothing yet**: the first thing to cut for low-power hardware, worth about 22% of the deferred overhead. Emissive is NOT dead, despite an earlier claim here: the light pass samples it at every non-sky pixel, so cutting it too (the other 22%) is a feature decision about emissive surfaces, not a free trim (see `docs/performance.md` 7.1).
- **Static-world culling is a LINEAR SCAN of every chunk in the world, five times a frame, and that is the engine's scalability wall.** `Scene.CollectVisible` walks `_staticWorldChunkList` end to end testing each chunk's render AABB against the frustum, and it runs once for the camera and once per shadow cascade. `--parts=<grid>` scales the demo's content to measure it: at 234 brushes ViewBuild is 0.04 ms and Shadows 0.17 ms; at 4,134 brushes they are 0.31 ms and 0.60 ms, while the number of DRAWS barely moves (150 casters to 154). The cost tracks the total world, not what can be seen, which is precisely backwards for the open-world pillar. **The world is already chunked on a grid and the culling does not use it.** An AABB sweep of grid cells is not the fix either, because a long camera frustum covers tens of thousands of mostly-empty cells; it wants a hierarchy over chunk bounds, rebuilt at swap time (rare) and queried per view (every frame). Mesh nodes already go through `SceneBvh` and cost nothing by comparison.
- **A subtractive PART brush is inert, and `Scene.InertPartBrushCount` is what says so.** The two declared bits are independent by design, and this is the one pairing that cancels: `Part` means "not in the placement list", which is exactly where a negative does its entire job, and only ADDITIVE parts get a mesh. So the brush carves nothing and draws nothing, and there is no error, no geometry and no hole to notice. It is counted rather than thrown because the editor converts whole selections between kinds in one command and a throw would refuse the whole operation for one brush. **This is also the answer to "should moving brushes stop interacting with the world": they already do, and it is called `BrushKind.Part`** — but a negative cannot be one, which is precisely why the pairing needs reporting.
- **The spatial index and the draw list want different populations, and conflating them was the single most expensive thing in a view build.** `SceneBvh` indexes everything carrying a `Brush` so picking, selection and raycasts can find world geometry, but a WORLD brush renders through the compiled static world and can never produce a draw. Building the draw list from that index therefore walked every brush in the level to find the few that draw: **measured at 1.16 ms of a 1.96 ms view build, to find 13 drawable nodes among 25,638**. `Scene.DrawableNodes` is now maintained beside the part and light sets, at the same three sites (`OnNodeAdded`, `OnNodeSpatialComponentChanged`, `MarkAdmissionChanged`), so drawability cannot drift from what a node carries. A list rather than a set because emission order feeds the draw list and must be deterministic; linear to scan, which is the right complexity because it is proportional to what can draw rather than to the world, and it wants to become a second BVH only once drawables themselves number in the thousands.
- **Static-world culling is clustered, and the chunk list is Z-ordered so that clustering can work at all.** A box over a run of 64 consecutive chunks rejects the whole run in one test. The first attempt gained almost nothing, because the list was sorted lexicographically by `ChunkCoord` and a run of 64 such cells is a 2,000-unit LINE whose bounding box intersects nearly every frustum. `ChunkCoord.MortonKey` interleaves the axes so a run is a compact block instead; `CompareTo` is deliberately left lexicographic because deterministic dirty-cell sets depend on it. Together with the drawable set: at 25,638 brushes the frame went **8.44 ms to 4.78 ms**, ViewBuild 2.09 to 0.48 and Shadows 2.67 to 0.20. The cost is `RebuildChunkClusters` running per swap, which put WorldSwap up from 0.59 to 0.95 ms; caching chunk bounds in a flat array parallel to the list would take most of that back.
- **Shadow acne is fixed by the RASTERIZER, and getting that wrong is what made shadows land in a different place on every face.** The depth pass draws each caster with a slope-scaled depth offset (`DepthBias`, `ShadowMap.RasterBias`, `Renderer.SetDepthBias`), which is `glPolygonOffset` on GL, a second rasterizer state on D3D11, and a field in the PSO key on D3D12 (a pipeline compiled for the camera pass would otherwise be handed to the shadow pass). **This is the only bias that attacks the cause.** Acne is a receiver comparing its own ramping depth against a stored depth that is constant across each texel, so their difference is a sawtooth whose height IS the primitive's depth slope, which is exactly what the hardware multiplies. **What it replaced was a normal offset scaled by `tan` and clamped at 8**, so a wall lit at sixty degrees had its sample pushed twelve texels off its own surface; because that push is along the NORMAL, the shadow slid centimetres sideways by a different amount on every face, and a shadow crossing a corner visibly failed to meet itself. The offset is gone entirely, not merely reduced: two dials for one defect is how the wrong one gets turned. Measured: with the raster bias on, a normal offset of zero is clean; with it off, the same frame is solid moire. `DeferredGlTests.A_lit_surface_with_nothing_over_it_is_not_shadowed_by_itself` fails (438 against 678) the moment `RasterBias` goes.
- **What is left on a shadow edge is RESOLUTION, and the fix for it is a rotated filter, not more bias.** A caster's silhouette is rasterised onto the map's texel grid, so a straight edge is stored as a staircase: one texel tall, and for an edge at a shallow angle to the grid, many texels long. Filtering spreads each step into a ramp but cannot shorten the runs between them, so a regular saw-tooth comb survives any kernel width, and a hardware `sampler2DShadow` would produce the same one. **Periodicity is what makes it visible**, so the four bilinearly weighted taps sit on a circle rotated by a per-pixel angle: the comb becomes grain for no extra fetches, and the frame is unchanged at 7.01 ms at 1080p on an Intel UHD 770. Proving this took a dump of the depth atlas itself; every argument from the shaded picture alone pointed at the filter, and the filter was correct. Spending more texels near the camera is the real remedy and is costed in `docs/performance.md` 5.2c.
- **A flat heap is not a healthy one, and the periodic stats line now says so.** The demo's managed heap sits at 4 to 20 MB and never grows, which reads as fine in any memory graph; it is flat because gen0 collects as fast as the engine fills it, and the real rate is **320 to 400 MB/s with 18 to 23 gen0 collections a second**. A gen0 collection stops every thread, the render one included, so that is a pause about every third frame at 60 fps, and a smoothed average frame time cannot show it. `SceneManager.DescribeMemory` reports the rate, the collection counts and the heap, and **splits off the render thread's own share** (`GC.GetAllocatedBytesForCurrentThread`, read on the render thread) because garbage made by a background compile costs a worker while garbage made in the frame costs the frame. Measured attribution: **0.59 MB per incremental static-world recompile** (555 compiles/s against 320 MB/s and 672 against 402, the same number both times), which is 93% of it, and about **18 KB per frame** on the render thread. The demo is a deliberate stress case here, since `PillarA` bobs as a WORLD brush to force a recompile every frame and the engine's own guidance is that a brush moving under simulation should be a `Part`. See `docs/performance.md` 9b.
- **Performance is a pillar, and the catalogue lives in `docs/performance.md`.** It records what the engine already does (frustum culling through a BVH for scene nodes, backface culling, mipmaps, chunking, incremental recompile, cascades, D3D12 mesh pooling), what a frame measurably costs (**0.85 us per visible draw, 0.22 us per TOTAL batch whether visible or not, 2.9 ms per megapixel on an Intel UHD 770, 27 KB of memory per brush**), and every technique worth adding with what each would buy here rather than in general. **Frustum culling is NOT missing** and neither is backface culling; occlusion culling, LOD, instancing, sorting and streaming are. The measured ceiling today is about **5 km² and 25,000 objects at 118 fps**. Do not act on any item in that list without measuring first: the two largest wins ever found here were a vsync call applied to the wrong thread and a validation layer nobody had turned off, and neither was reachable by reading code.
- **The engine already emits instancing batches, and every measurement ever taken here was blind to them.** `PartBrushMeshCache` keys on brush **reference identity**, so N part-brush nodes sharing one `Brush` instance resolve to one GPU mesh and `Scene.CollectVisible` emits N `RenderItem`s with the same mesh, the same material and N different world matrices. That is a batch, sitting in the draw list, uncollapsed. Nothing measured it because **no scenario in the repo repeated a mesh**: static-world chunks are unique geometry by construction, and `--parts` gives every scattered brush its own randomized extents, so the profile numbers were taken on a draw list with zero duplicates in it. `--props=<count>` is the fixture that closes that hole, and it moved the answer by more than four times: at 8,000 props, **3.7 ms of a 5.24 ms frame is duplicate draws of one mesh** (Shadows 2.26, Geometry 1.53, against a 0.10 ms baseline), because a caster is redrawn per cascade. Two things this corrected in the written plan, both stated confidently and both false: that Roblox-style parts were "already served by CSG merging" (true of `BrushKind.World`, false of `BrushKind.Part`, which is the kind the engine's own guidance tells you to use for anything repeated), and that `R12` was renderer plumbing (SpectraShade has no per-instance vertex input and no `InstanceId` at all, and `uModel` is a `cbuffer` uniform rewritten per draw, so it is a compiler feature first). **`ViewBuild` survives instancing** and is the other half: submission is not selection.
- **Instancing landed for the geometry pass too, and it is worth about nine times the pass.** `Renderer.DrawGeometry` is the whole deferred draw list — batches as instanced draws, then what no batch claimed, then the static world's chunks — and it is **shared by all three backends rather than written once per pipeline**, because the only things that genuinely differ are `BindsProgramBeforeUniforms` and `ClipZCorrection`, both already stated once. Measured on the demo at `--props=2000`: 560 of 562 visible props collapse to 2 draws, the Geometry phase goes **1.80-2.62 ms to 0.21-0.24 ms**, and the frame goes about **3.9 ms to 3.2 ms** on D3D11. Three things are load-bearing. **The view and projection writes belong INSIDE the per-batch loop**: on both D3D backends they are staged into a constant shadow that `Use()` flushes, so hoisting them makes every batch after the first draw with the previous batch's material — and on OpenGL it would appear to work, which is the worse half. **A null material is skipped exactly as the item loops skip it**, and `GeometryDrawsSaved` is therefore counted from what was actually drawn rather than from `view.DrawsSaved`, which does not know about the skip. And **`Batches` plus `SingleItems` is exactly `Items`**, so a pipeline that draws all three doubles every surface. **The first frame a batch appears is always drawn unbatched**: the buffer is sized at a frame boundary from the previous frame's high-water mark, which is what keeps every allocation outside an open pass, so a test that renders one frame measures only the fallback and passes just as happily with the instanced path entirely broken (`GeometryInstancingGlTests` renders two, and its fixture uses **two interleaved groups** so the second batch has a non-zero offset — with a single batch the offset is always zero and a whole class of indexing bug still draws the right picture).
- **Instance buffers rewind once per FRAME, not once per pipeline execution, and only D3D12 can see the difference.** With `ProbeTarget` set a frame renders the scene twice, into the probe and then into the window, both in one command list; rewinding between them puts the second run's transforms under the first run's already-recorded draws. It was harmless only because both runs draw the same scene. `Renderer.BeginFrameInstanceBuffers` now does the sizing and the rewind for both buffers at the top of every backend's `Render`, and **growth happens there and nowhere else** for the same reason cascades never grow between themselves.
- **Instancing landed for the shadow pass first, and the two bugs it shook out are both "silent on one backend, fatal on another".** `[PerInstance]` in SpectraShade reports a vertex-input signature the renderer builds layouts from; `InstanceBuffer` and `Mesh.DrawInstanced` exist on all three backends; `RenderView.BuildBatches` groups `(Mesh, Material)` **by first appearance rather than adjacency** (the draw list is emitted in spatial-index order, so copies of one prop arrive interleaved and run-merging would find almost nothing) and that **reorders draws, which is safe only because every item in it is opaque** - blended geometry needs its own sorted pass and must not join this partition. **Growing the instance buffer between cascades frees a resource the open command list still references**: D3D11 executes immediately and survives it, D3D12 removes the device with `DXGI_ERROR_DEVICE_HUNG`, so all growth happens before the pass opens from the previous frame's high-water mark and a frame whose demand jumps draws those batches unbatched once. **A D3D11 input layout is bound to the shader signature it was validated against**: building the combined two-slot layout against the DEFAULT shader creates successfully and then fails every draw with "the input stage requires Semantic/Index (TEXCOORD,3) ... not provided by the output stage", so `CreateInstanceBuffer` takes the program it will be drawn under (GL and D3D12 ignore it - GL binds attributes into the VAO, D3D12 into the PSO). **The measured win was a tenth of the projection**, and the reason is the lesson: a phase total is not a submission cost. See `docs/performance.md` 6.1.
- **A shader's instanced twin is GENERATED, not authored, and that decision is what makes instancing cheap to adopt.** `[PerInstance]` on a `mat4` cbuffer field tells the compiler to emit a SECOND vertex stage from the same source, with that uniform arriving as a per-instance vertex input at the first free location; the ordinary stage is emitted byte-for-byte unchanged, so a single draw keeps the uniform path and pays nothing for the variant existing. The two alternatives both lose. A hand-written twin per shader duplicates the whole vertex stage and every future shader owes the same copy - fine for `ShadowDepth`, which is why it was written that way first, and not fine for `GBufferFill`, whose five-attachment write this file already names as a contract two shaders can drift on. Sharing a body through `import` is not available at all: **`import` parses into `CompilationUnit.Imports` and is never resolved, there is no resolver anywhere in the compiler**, and `FEATURES.md` claimed otherwise until this landed. **The rewrite is three edits and NO expression rewriting**, which is why neither code generator changed: the field leaves its cbuffer, an identically named per-instance field joins the vertex input struct, and the vertex body gains one leading local (`mat4 uModel = input.uModel;`) that keeps every existing bare reference resolving. Running the same generator over the rewritten AST is also what stops the two stages drifting - there is no second emission path. One marked uniform per shader and `mat4` only, both refused rather than guessed at, since the location span and the instance stride follow from the type.
- **A workflow agent can edit the working tree, and one did.** A perf-audit subagent left `Console.WriteLine` instrumentation inside the static-world swap. It was caught because `git status` disagreed with what this session had written. Check the tree after any agent run that had write access, and never trust a measurement taken across one. **Checking once, before committing, is not enough**: a gizmo review's agents wrote four probe files and edited a source file *between* a clean `git status` and the `git add` two commands later, and one probe went into a commit. While an agent with write access is still running, the tree is not yours — verify immediately before `git add`, or stop the agents first. (Their probes were worth reading before deletion: two of the confirmed defects in that review were found by exactly those files.)
- **A committed probe is still instrumentation, and one shipped a silent rendering bug plus a tainted baseline.** Commit 0666406 left TEMP-PROBE redundant-state experiments in both D3D backends. The D3D11 half cached the last SRV/sampler pair per PROGRAM and was never reset when the context's slots were cleared behind it (BeginPass's offscreen unbind, ClearState on resize), so from the second frame on, D3D11 passes skipped rebinds against nulled slots and sampled null SRVs: zeros by definition, no exception, no debug-layer message, invisible to `--offscreen-probe` (it reads error counts), to the screen probe (a raycast) and to the pixel tests (GL-only). Every D3D11 number in `docs/performance.md` §3 was measured on exactly those frames. The rule the fix encodes: **a skip cache lives beside the STATE it mirrors and is reset by every site that clears that state.** The cache is context-level now (`D3D11BindCache`, pinned by `D3D11BindCacheTests`), §3 carries the baseline caveat, and the D3D12 half (dead `ProbeBound*` fields) became the real thing: last-bound root signature/PSO/topology/root-CBV tracking on the renderer, reset at the frame's list reset, which also deleted most of the deferred pass's per-draw state re-issue. The DXGI factory debug flag was the one residue the 0c00850 validation gate missed (requested unconditionally, so DXGI validated Present in every build on any machine with Graphics Tools) and now obeys `EnableDebugLayer` like everything else.
- **A mesh's CPU copy is opt-in, because the two mesh populations want opposite answers.** A mesh NODE's mesh is raycast for picking, measured for BVH bounds, and drawn as a debug wireframe, all off CPU arrays. A static-world chunk mesh or part-brush mesh is read by nothing (chunks cull by the artifact's render bounds and query through the BSP, parts pick through their brush planes), yet every one retained positions/normals/indices anyway: per-(cell, material) garbage on the render thread at every landed recompile (the largest attributed slice of the ~18 KB/frame in `docs/performance.md` 9b) plus a permanent second copy of all world geometry on the managed heap. `CreateMesh` now takes `MeshCpuAccess` (chunk and part meshes pass `None`); `LocalBounds` is computed for every mesh either way, straight off the upload stream, and `Mesh.HasLocalBounds` is what says the bounds are real, so consumers never infer validity from the arrays. `SceneBvh`'s unit-box fallback reads it.
- **The physics static tree is never rebuilt per sync.** Box3D inserts and removes static leaves at shape create/destroy time (`b3CreateShapeProxy`), so the per-sync `b3World_RebuildStaticTree` the first sync implementation ended with (an API whose own header says "internal testing", exactly as `docs/physics.md` warned) was pure quality re-optimisation costing O(world log world) on the render thread every frame a world brush moved, quietly falsifying the world-size-independent footing the dirty-cell sync exists for. It now runs once per full compile (bulk creation, its intended use) and otherwise only after NET shape churn passes a quarter of the world's static shapes (floor 256): net, because the steady state of an animating brush is the same cell destroyed and rebuilt with near-identical AABBs, which barely degrades the tree, and counting it gross would re-arm a world-sized rebuild forever. `Box3DScenePhysicsTests` pins both sides, including 160 in-place edits accruing nothing.
- **Shadows cost about what a second geometry pass costs, and the honest number is in the stats line.** Four cascades roughly double the demo's frame (D3D11: 0.38 ms without, 0.75 ms with), because they are four more depth passes over the scene and add roughly 150 draws to 40. Deferred itself is nearly free at this scene size. **`D3D12Renderer.Present` still calls `WaitForGpu()` every frame**, so CPU and GPU never overlap and the frame is their sum rather than their maximum; that is why Present is now the backend's largest phase and it is the next thing worth fixing.
- **A light rig is tuned to a BRDF, and the two changed at different times.** The forward shader was `albedo * N.L * radiance` with no normalisation; a real Lambert term divides by pi, so the moment deferred landed, every light in the demo was worth a third of what it had been. Nothing failed and nothing warned: the scene simply read as a dark room, and the shadows that had just been built were invisible in it because there was no lit surface for them to darken. Both shaders now divide by pi and the demo's intensities are stated for that, so the two paths can share one rig. Expect the same the next time the shading model changes.
- **A directional light's direction comes from the node's forward axis, and it is authored as a direction, not as euler angles.** `Light.RotationForDirection(travel)` builds the rotation whose forward axis is the given direction; typing a yaw and a pitch instead is how the demo's sun spent its whole existence shining upward from below, because the pitch that reads like "tilted down" raises the third row of the rotation. Nothing errors and nothing warns: the scene is merely dim with its lit side facing away from every camera anyone points at it. `SceneLightTests` pins the round trip.
- **Rendering goes through a pass, and a pass names its target.** `BeginPass(target, clear)` / `EndPass()` on the renderer is the only way anything binds a render target, sets a viewport or clears; the six pipelines used to do all three themselves from a backend-specific context, which was six copies of one decision. **Everything sizing itself reads `Renderer.PassSize`, never `FramebufferSize`** (viewport, `camera.AspectRatio`, and therefore the projection and the frustum built from it), because the two are equal only while every pass goes to the window, and a leaked window size renders a stretched picture that nothing reports as an error. Passes do not nest and a mismatched pair throws, since a silently wrong binding is a corrupt picture on one backend and a debug-layer message on another. A `RenderTarget`'s colour attachment is a **plain `Texture`**, so shadows, post and material previews reuse the existing material/sampler path and no new binding concept enters the engine; **its object identity survives a resize** (the GPU handle is swapped inside the wrapper, the same trick `ShaderProgram.TryReload` uses) or every material sampling an editor viewport would point at a destroyed texture the first time a pane moved. Depth is a bool rather than a format, and it IS sampleable — a plain `sampler2D` returns the depth value in `.r` on all three backends (the deferred light pass and the world-line blend pass both rely on it); what `R6` adds is hardware-compare sampling (`sampler2DShadow`), not readability. On D3D12 each target **tracks its own resource state** and emits a barrier only on a real change, and the PSO's target state comes from the open pass: a pipeline compiled for the back buffer and bound to a target with another format is a validation failure, not a wrong pixel. **The D3D backends have no headless device fixture, so `--offscreen-probe` is their test**: it renders real frames into a real target, resizes it, and fails if `Renderer.DebugLayerErrorCount` moved, which is the only way a missing barrier is ever reported.
- **All shading happens in linear light, and every conversion is done by hardware.** A texel in a PNG is a display code, not a quantity of light, so it is decoded on the way into the shader and the result is encoded on the way to the screen. Both conversions are **format flags, never a `pow()` in a shader**: the sampler decodes *before* filtering, so bilinear taps and mip levels average light rather than codes, which is exactly the difference between a tiled brush wall that holds its brightness into the distance and one that darkens. The classification is a fact about the content, not about sampler state, so it lives in the content. A `.spectramat` texture line takes `srgb` (the default, because an image is a picture unless its author says otherwise) or `data` for anything the shader does arithmetic on, and the keyword is `data` rather than `linear` because `linear` already means bilinear on that same line. **Colour space is part of the texture cache key**, alongside filter and wrap, because one image is legitimately albedo in one material and a mask in another, and those need two GPU textures. A **`color`** directive is authored in sRGB and stored linear (alpha never converted); a **`vec3`** is numbers and passes through untouched, which is the whole rule of the format. `R8` is always linear because no backend has a one-channel sRGB format: `TextureFormatInfo.Resolve` is the single place that rule lives, and `AssetManager` is the layer that reports the downgrade, because it is the only one that knows the path. **Each backend names sRGB where its own swap model allows it.** D3D11's bitblt chain is created `_SRGB`; D3D12's flip-model chain may not be, and gets an `_SRGB` RTV over a `_UNORM` buffer instead, which is why `D3D12TargetState.BackBuffer` carries the *view* format (a PSO is validated against the view, not the resource). **OpenGL cannot get an sRGB window at all** through Silk.NET 2.23, because `GLFW_SRGB_CAPABLE` has no `WindowOptions` field and a hint set from outside is wiped by Silk's own `glfwDefaultWindowHints`, so GL renders into an `SRGB8_ALPHA8` renderbuffer and blits out with encoding off (`OpenGLSrgbTarget`, the engine's first offscreen target and a down payment on `R3`). Doing this half-way is worse than not at all: before it, the engine was wrong twice in opposite directions and the errors partly cancelled, so shipping only the texture decode would have left one backend visibly darker than the other two.
- **Shaders are written in SpectraShade** (`.spectrashade` files, real files not string literals — see `Graphics/BaseShaders/`), compiled at runtime per backend, hot-reloaded on save in dev builds.
- **Content is real files under `Assets/`**, never string literals or byte arrays in code, and it is copied to the output beside the executable so a deployed build resolves the same relative paths (`ContentRoot` — the repo folder wins in a developer build, so hot-reload watches the files you actually edit). Materials are hand-parsed `.spectramat` text (`Assets/Materials/`, spec in `Assets/MaterialParser.cs`): `shader`, `texture <sampler> = <path>[, filter][, wrap]`, and `float`/`vec2`/`vec3`/`vec4`/`color` parameters, with unknown keys warning rather than throwing so files stay forward-compatible. **Content errors must never reach the draw loop**: a missing material degrades to `AssetManager.DefaultMaterial` (non-null for the manager's whole life), a missing texture to the magenta placeholder, and a material with no shader is skipped by the pipelines — each with a warning.
- **The asset system is one manager over typed caches, split along the threading contract.** `AssetManager` owns a cache per asset kind (textures, materials, models), each keyed by normalised content-relative path so two spellings of a path share one entry and one GPU resource. Every kind has both entry points: a synchronous `Load*` for load time (decode/import AND GPU creation on the render thread; it throws so a load-time caller can decide) and a `Request*` for while frames are running (returns a handle immediately — placeholder-bound texture, not-yet-ready model — hands the pure-CPU decode/import to the thread pool, and reports failure on the handle rather than throwing). Results cross back through a `ConcurrentQueue` that `PumpPendingUploads` drains once per frame on the render thread, which is where every GPU resource is created — same shape as `ShaderHotReloader`. **The manager owns everything it hands out**: callers never dispose a texture or mesh, they `Unload*` or let `ReleaseGraphicsResources` (render thread, before `Renderer.Shutdown`) clean up. Textures hot-reload through one `FileSystemWatcher` per directory, with a per-asset sequence ticket so a stale decode can never overwrite a newer one. Model materials resolve in descending authority: an authored `Materials/<name>.spectramat`, then the diffuse texture the model file named, then the default material.
- **Audio is a real device now, and the one thing it never uses is `AL_LOOPING`.** `AudioManager` opens the default OpenAL device, owns one context, one listener and a pool of 32 sources, and hands out voices; it is shaped after `AssetManager` on purpose, because the two answer the same question (a resource the render thread owns, created on one thread and pumped once a frame). **The loop-point rule is the whole of the design.** OpenAL's looping flag repeats a WHOLE buffer, so it can express exactly one region, the entire sound, and music with an intro or ambience with a pickup bar has nowhere to put its loop points. So a loop is buffer-queue arithmetic in SAMPLE FRAMES (`AudioLoopCursor` plans the runs, `StreamingVoice` gathers and uploads them), frames rather than bytes or seconds because bytes break on a channel-count or sample-width change and seconds cannot be sample-accurate, and the flag is explicitly CLEARED on every pooled source since a handle is reused. `IAudioBackend` is a deliberately small seam over the AL calls the engine actually makes, and it has no member through which looping could be asked for at all; a convention test holds that and the one-and-only `SourceBoolean.Looping` write. **A buffer is not a loop iteration**, which is why a region shorter than one buffer, a region whose length is not a multiple of the buffer size and a seek into the middle of a loop are all the same case rather than three. Three failures are invisible without naming them. **A starved streaming source reports `Stopped` exactly as a finished one does**, so the pump discriminates on QUEUE DEPTH and restarts, or music ends permanently after one frame hitch with nothing logged, and the source POOL exempts streaming entries from its state scan for the same reason (it also never steals one: a footstep is dropped instead). Reclaim order is free, then the OLDEST FINISHED, then a steal that is counted. **`alGetError` is a single latch per context**, so two threads calling AL turns every error check into a coin flip and a failed upload reports success: the render thread owns this class, exactly as it owns the asset manager's GPU half, and the per-frame `Update` sits beside `PumpPendingUploads`. `Initialize` and `Shutdown` run on the main thread for the one reason they are safe there, that the render thread provably does not exist yet or has been joined; the AL context is process-wide current by spec, and OpenAL Soft's thread-local-context extension is deliberately NOT used. **No device is DISABLED MODE**, one warning line naming the reason and every later call a no-op, because a machine with no sound card must still run the engine. `Silk.NET.OpenAL.Soft.Native` is referenced by no C# file and is not optional: Windows has shipped no OpenAL runtime since 2007, and with bindings alone every machine falls into that disabled mode. **Real playback is a manual gate, never a test** (CI has no sound card, and a test that needs one is a test that gets disabled), so the pool, the reclaim policy, the loop arithmetic and the disabled path are proved against a fake backend instead.
- **Brush faces carry their own material and Hammer-style texture axes.** `FaceSurface` (one per brush plane, immutable with the brush — retexture via `Brush.WithFaceMaterial`, which returns a new instance and is exactly what invalidates that brush's cached carve) holds a `MaterialRef` plus U/V axes, scales in world-units-per-repeat, and offsets in repeats; zero axes mean *world-aligned*, deriving the projection from the face normal by the dominant-axis rule (Hammer's default, and bit-identical to the projection the engine used before per-face surfaces existed). Explicit axes are texture-locked through rigid transforms — the axes rotate and the translation folds into the offsets, so a dragged brush keeps its texture glued to the surface. **The CSG payload is a pure value: an interned material ID, never an asset object.** That is what lets the payload ride through the whole background compile (carve → snap → weld → BSP → per-material mesh split) with no GPU handle or asset-manager state on a worker thread; `MaterialRegistry` interns paths to append-only IDs so one stays meaningful for the process's life, and `AssetManager.ResolveMaterial` turns it into a real material exactly once, on the render thread, at mesh-upload time.
- **A map is a FOLDER of text, and the only binary artifact is the cook's.** `MyMap.smap` is a directory holding `map.json` (and, once scripting lands, `scripts/*.luau` as real files); `SpectraEngine.Core/Maps/` reads and writes it with a hand-rolled `Utf8JsonReader`/`Utf8JsonWriter` codec, no reflection, AOT-safe by construction. The promise is not "the editor can reopen its own file", it is **a person edits `map.json` in VS Code, saves, and the editor does not fight them** - which is what makes three rules the feature rather than spec compliance: byte identity per file, unknown-member preservation, and a save that writes only files whose content changed (temp file plus rename) and never touches a file it does not reference.
  - **The codec goes through a `MapDocument`, never straight to `SceneNode`, and there are two independent reasons.** Preservation has to park bytes somewhere, and a `SceneNode` is the wrong place: that blob would then have to survive clone, reparent, undo and the id index. And **a scene is a LOSSY image of a document** - `Brush`'s constructor re-normalises every plane it is handed, so a hand-authored `[2,0,0,-64]` comes back out of a `Scene` as `[1,0,0,-32]`. That is a canonicalisation rather than a defect, but it means the scene can never promise to reproduce the bytes it was built from and the document can. So the two round trips are **separate claims tested separately**: `Write(Read(bytes)) == bytes` is exact; save/load/save over a real level is exact **from the second save on**, and `MapLevelFidelityTests` pins both against `DemoPlayArea` by comparing compiled chunk meshes vertex for vertex (a 2 mm shift in one plane offset fails it).
  - **Members the engine has not built yet are carried, not dropped**, in three tiers. Bound (id, name, kind, transform, brush, light, children); **reserved** (`editor`, `realm`, `state`, `kind`) which are known by name and *validated* even where no enum exists yet, because a mistyped `"prt"` surviving as an opaque member falls through to `World` and **re-admits a part brush to the carve**, a world-topology change on load; and preserved (`entity`, `script`, `scene.spawn`, anything future). A `brush` record is **closed** - an unrecognised member is a reader error - while a `face` record is **open**, because per-face authoring is where the format grows and none of it changes what the solid is.
  - **Preserved members carry an ANCHOR into the canonical member order.** The spec says to collect them into an ordered list and replay them, and never says where; replaying at the end of the object satisfies every stated rule and still changes the bytes for exactly the case preservation exists for, since a newer engine wrote its own members interleaved among ours. Two further spec defects found and fixed here: the preservation recipe as written **emits the property name twice** (it captures the span from the name and then replays with `WritePropertyName` + `WriteRawValue`), and the `.gitattributes` entry `*.smap/**` **matches nothing that matters** - attribute patterns use gitignore syntax, where a separator in the middle anchors to the file's own directory, so it catches a bundle in the repo root and misses `MyGame/Maps/Lobby.smap/map.json`; it needs `**/*.smap/**`, verified with `git check-attr` because the failure is silent.
  - **Two writer settings are load-bearing and both fail silently.** `Utf8JsonWriter.NewLine` defaults to `Environment.NewLine`, so a writer that leaves it alone emits CRLF on Windows and LF elsewhere and byte identity holds only within one operating system; and `WriteRawValue` **does not indent raw content at all**, so planes and faces need their own layout or six planes arrive on one line with the closing bracket alone on the next. Records are one per line because a plane and a face are each the unit a person edits, and the file ends with a newline because it is a file in a git repository before it is anything else.
  - **A mesh node names its MODEL, not its geometry.** `SceneNode.MeshSource` is the `(model path, submesh index)` pair `ModelInstantiator` already knows while it builds each node and used to throw away - a `Mesh` carries no name, path or owning-asset reference, and `Renderer.CreateMesh` takes raw spans, so there is no moment at creation time when an origin *could* be recorded. Detaching the renderer clears the source, because one that outlived the mesh it described would make a save name an unrelated model; `Clone` copies it *after* the renderer for the same reason. A load that cannot resolve the model **degrades to a node with no renderer plus a line in `MapLoadReport`**, deliberately the opposite of the brush path, which throws: a brush that cannot be built is a hole in the world, a missing prop is a missing decoration. **A mesh built in code still cannot be saved and never will be** (`Primitives.Cube()` names no file); the demo's seven remaining warnings are exactly those, and `MapSaveReport` says so.
- **A PROJECT is a folder too, and only `cooked/` is ever binary.** `SpectraEngine.Core/Projects/` owns `MyGame.spectraproj` (the manifest, and the double-clickable identity) plus the canonical layout: `Assets/` (the content root, unchanged), `Maps/` (bundles, which are directories), `Scripts/`, and `cooked/` (derived, gitignored, never authored). `ProjectLayout.Open` takes the file **or** the folder, because both are what a person means; a folder holding two manifests is **refused rather than guessed at**, since the guess would be alphabetical. **Maps are plural and first-class** - the manifest lists them in the author's order and names a `startupMap`, while `DiscoverMaps()` walks `Maps/` for what is actually there, and both are deliberately real: the manifest is what a cook bakes, the folder is what somebody dropped in, and an editor reconciles them rather than one silently winning. Scaffolding **never clobbers a file that already exists**, and ships a `.gitignore` and a `.gitattributes` because both are load-bearing rather than tidy. `--save-project` exports the running scene as one, copying the whole content root: working out which files a map *needs* is the cook's dependency walk, and a worse guess at it here would ship projects missing one texture nobody noticed. `--project` then runs it, with the project's `Assets/` as the content root and its `startupMap` as the level (verified end to end: probe PASS, self-test PASS, zero errors, entirely out of an exported folder).
  - **The canonical-JSON rules live in ONE place** (`Serialization/CanonicalJson`), shared by the map and the project, because the settings in them fail silently and a second copy is a defect waiting for somebody to fix one and not the other: `NewLine` defaults to `Environment.NewLine` (CRLF on Windows, so byte identity would hold only within one OS), the default encoder escapes `+ < > &` and all non-ASCII into unmergeable noise, and `WriteRawValue` does not indent raw content at all.

## Key Constraints

- **AOT compilation**: all code must be AOT-compatible — no reflection-heavy patterns, `dynamic`, or runtime codegen. `PublishAot` is on for `SpectraEngine.Executable` and `SpectraShade.Compiler.CLI`; `IsAotCompatible` is on for `SpectraEngine.Core`, so the trim/AOT/single-file analysers run on Core's ordinary build rather than only at publish time. A NativeAOT publish of the demo runs on all three backends today. The one thing AOT breaks that a JIT run hides is Silk.NET's reflection-based backend discovery — every host must call `SilkPlatform.EnsureRegistered()` before `Window.Create`/`CreateInput`.
- **Nullable reference types** are enabled solution-wide; all code must be null-safe.
- **Threading**: the render thread owns the GL context, scene updates, and GPU resource creation; the main thread pumps OS events. Cross-thread state goes through the established channels (InputManager lock, volatile title, latched resize, **latched cursor mode**, **latched window mode**, hot-reload queue). GLFW cursor calls are window-thread affine like the title and the window size, so the editor camera *requests* a cursor mode through `ICursorLock` (implemented by `InputManager`) and `Engine.Run` applies it with `ApplyPendingCursorMode()` in the same slot it applies the title; `IWindow.FocusChanged` is wired straight to `InputManager.OnWindowFocusChanged`, which force-releases the lock and drops held keys/buttons so a lost focus can never strand a captured cursor.
- **The engine owns fullscreen, and it is borderless windowed — DXGI never drives a mode transition.** Left alone, DXGI keeps its default Alt+Enter handling and runs its own `SetFullscreenState` *inside the window procedure*, i.e. on the main thread, while the render thread is presenting and calling `ResizeBuffers` on the same swap chain; both D3D backends therefore call `IDXGIFactory::MakeWindowAssociation(hwnd, DXGI_MWA_NO_ALT_ENTER)` **on the factory that created the chain, before releasing it** (the association is per-factory — making it on a second factory silently does nothing). Fullscreen is then the fourth main-thread latch, the exact shape of the cursor one: any thread calls `IWindowModeLatch.ToggleFullscreen()`/`RequestWindowMode` (`Engine.WindowMode`, bound to **F11** in the render loop beside F1–F6), `Engine.Run` applies it with `WindowModeLatch.ApplyPendingWindowMode` in the same pump slot as the title and the cursor, and the existing framebuffer latch carries the new size to whichever backend is running. `WindowModeLatch` is a pure state machine over `IWindowModeTarget` (bounds, decoration, maximized, display bounds) so it is headlessly testable; `SilkWindowModeTarget` is the only piece that names a windowing backend — and reads the display size from the **video mode**, because Silk's GLFW `IMonitor.Bounds` is the *work area* and filling that leaves the taskbar on top. No exclusive fullscreen, ever: with a flip-model chain, borderless is equivalent and avoids mode switches, device-lost transitions and the `SetFullscreenState(FALSE)`-before-release shutdown rule. **The OpenGL backend gets the identical toggle for free** — nothing in the path touches a graphics API.
- **`new ComPtr<T>(p)` AddRefs — every wrap of a freshly created COM pointer must hand its reference over** (`ComOwnership.Own`, which wraps and releases). Silk.NET's `ComPtr<T>` has WRL semantics: it *shares* a pointer rather than adopting one, so wrapping a `Create*`/`GetBuffer`/`QueryInterface` result leaves the object at two references and disposing the `ComPtr` only ever drops it to one. On the swap-chain path that is not a leak but a crash: DXGI refuses `ResizeBuffers` with `DXGI_ERROR_INVALID_CALL` while any back-buffer reference is outstanding, so **every** D3D12 window resize failed (D3D11 hid the same trap one level down, in the leaked RTV that holds the back buffer). Everywhere else it is an unbounded leak, and the rule is therefore all-or-nothing: **no resource is too small**, because the hot paths are the small ones — the per-mesh vertex buffer, index buffer and input layout, recreated for every chunk each static-world recompile touches, grew the ordinary demo by 2.2 GB in thirty seconds on D3D11 and 1.2 GB on D3D12 while an OpenGL control run stayed flat. Both are flat now, and `ComPtrOwnershipConventionTests` fails the build's test run if any `Graphics/` source ever writes `new ComPtr<T>(p)` again — the fix that converted only the swap-chain sites and left twenty others is exactly the mistake that test exists to catch. **The mirror rule is `ComOwnership.Release(ref field)` for letting go**: `ComPtr<T>.Dispose()` does *not* null the handle, so with one reference instead of two a second release is an over-release rather than something the leak absorbed — and both renderers can genuinely reach one (`ReleaseBackBufferViews` runs on the resize path and again at shutdown with a device loss able to throw in between, and `Engine.RenderLoop`'s crash handler calls `Shutdown` a second time when the first one threw). Every renderer-owned field release goes through it and is idempotent; `ComOwnershipTests` pins all of this against a hand-built COM object (vtable + counter, no GPU). `DrainPendingResize` on both backends is also resilient now: `SwapChainResizePolicy` decides whether to touch the chain at all (unchanged size, no chain, dead device, degenerate/minimised size, a size that already failed), a device loss ends the run as a `GraphicsDeviceLostException` carrying `GetDeviceRemovedReason`, and any other failure logs the HRESULT, rebuilds the views at the OLD size and keeps rendering — a released-buffers-and-no-views state would turn one bad resize into a guaranteed crash next frame. `DxgiDebugMessages` drains DXGI's own info queue, which is where swap-chain rejections are explained and the device info queues are silent.
